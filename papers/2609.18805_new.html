ProgramDistill: From Interactive Web Apps to Verifiable Reference-Guided SWE Tasks

프로그램디스틸: 인터랙티브 웹 앱에서 검증 가능한 참조 기반 SWE 과제로

동작하는 참조(reference) 웹 애플리케이션과의 상호작용만으로 숨겨진 요구사항을 추론하고, 이를 코드로 복원한 뒤 실제 리플레이로 검증하는 완전 자동화 파이프라인(mine-craft-patch)을 통해, 4,063개의 재현 가능한 SWE(소프트웨어 공학) 과제로 구성된 벤치마크 ProgramDistill을 제안한다.

한 줄 요약

동작하는 참조(reference) 웹 애플리케이션과의 상호작용만으로 숨겨진 요구사항을 추론하고, 이를 코드로 복원한 뒤 실제 리플레이로 검증하는 완전 자동화 파이프라인(mine-craft-patch)을 통해, 4,063개의 재현 가능한 SWE(소프트웨어 공학) 과제로 구성된 벤치마크 ProgramDistill을 제안한다.

배경 및 문제의식

기존 코딩 에이전트 평가(SWE-bench 등)는 이슈나 지시문의 형태로 "원하는 동작"이 이미 명시되어 있다고 가정한다. 그러나 실제 웹 개발에서는 개발자가 이전 버전 제품, 프로토타입, 유사 애플리케이션, 데모 영상 등 동작하는 소프트웨어 자체를 보고 의도된 동작을 추론해야 하는 경우가 많다. 인터랙티브 웹 애플리케이션은 UI 조작과 애플리케이션 상태가 얽혀 있고, 로그인 후 객체 생성, 생성 후 수정처럼 선행조건(prerequisite)이 있는 동작들로 구성된다는 점에서 특별한 구조를 갖는다. 저자들은 이런 '동작하는 참조 애플리케이션'을 관찰해 숨겨진 사양(specification)을 스스로 발견하고 복원해야 하는 문제, 즉 "참조 기반 소프트웨어 공학(reference-guided software engineering)"을 다루는 확장 가능한 벤치마크가 없다는 점에 착안했다.

핵심 기여

  1. 참조 기반 SWE 벤치마크: 26개 인터랙티브 웹 애플리케이션에서 발견한 1,975개의 재현 검증된 동작(behavior)을 바탕으로, 원자적(atomic) 수정부터 누적(cumulative) 수정, 전체 애플리케이션 재구성까지 아우르는 4,063개의 재현 가능한 SWE 과제를 구축했다.
  2. 프로그램 증류(program distillation) 개념화: 애플리케이션을 다양한 세밀도의 기능 단위로 쪼개는 "애플리케이션-과제 분해(application-to-task factorization)"와, 참조 애플리케이션에서 관찰한 동작을 실제 코드 수정으로 옮기는 "참조-현재 증류(reference-to-current distillation)"라는 두 축을 정의하고, 사람의 개입 없이 이를 자동화하는 mine-craft-patch 파이프라인을 구현했다.
  3. 복원 깊이(restoration depth) 축 도입: 선행조건 계보(lineage)를 따라 과제를 조합함으로써 원자적 수정에서 전체 재구성까지 난이도를 통제할 수 있는 축을 제공하고, 이를 통해 복원 깊이가 커질수록 코딩 에이전트의 성능이 체계적으로 저하되는 현상을 드러냈으며 향후 커리큘럼 학습의 기반으로 제시했다.

방법론

mine-craft-patch 파이프라인은 세 단계로 구성된다.

Mine(채굴): 각 애플리케이션을 프로덕션 빌드(참조 인스턴스)와 개발 서버 버전(수정 가능한 인스턴스)으로 동시에 서비스하고, Playwright 기반 브라우저 헬퍼로 상호작용한다. LLM 에이전트가 소스와 UI 근거를 바탕으로 행동 목표를 제안하고 실제로 애플리케이션을 탐색해 궤적을 얻은 뒤, 깨끗한 초기 상태에서 다시 수집해 불필요한 탐색 단계를 제거한 재현 가능한 트레이스(τ)를 만든다. 이 트레이스는 리플레이 검증기(V)를 통과해야만 채택되며, 부모 트레이스를 연결해 선행조건 계보(lineage)를 구성한다.

Craft(제작): 검증된 트레이스에서 해당 동작을 구현하는 소스코드를 찾아 마스킹(mask)하여 수정 과제로 변환한다. 마스킹 범위는 로직만 제거하는 방식과 로직+UI를 함께 제거하는 방식으로 나뉘며, 하나의 동작만 마스킹하는 "원자적 과제"와 계보를 따라 여러 마스크를 결합하는 "누적 과제"로 구성을 통제한다. 마스크가 유효하려면 마스킹된 애플리케이션이 빌드·실행되고, 선행 동작들은 여전히 통과하되 목표 동작만 실패해야 한다(SWE-bench 스타일의 fail-to-pass/pass-to-pass 조건). 별도의 LLM 기반 "마스크 깊이 심사자"가 표면적인 변경(예: 기능 플래그 토글)을 걸러낸다.

Patch(수정): 코딩 에이전트가 마스킹된 저장소와 문제 설명을 받아, 참조 애플리케이션과 비교하며 코드를 수정한다. 부분 애플리케이션 재구성(masked repository에서 시작)과 전체 애플리케이션 재구성(최소 실행 골격에서 시작)의 두 가지 설정으로 평가하며, 각각 이진 점수(전체 계보 통과 여부)와 체인 점수(복원된 접두사에 대한 부분 점수)로 채점한다.

실험 설정 및 결과

GPT-6 Astra, GPT-5.6 Sol, Claude Opus 5, Claude Sonnet 5, Gemini 3.7/3.6 Flash, Gemini 3.1 Pro Preview, Grok 4.6, GPT-5.3 Codex 등 9개 최신 코딩 에이전트를 R2E-Gym 기반 하네스로 평가했다(고비용 문제로 300개 과제로 구성된 ProgramDistill-300 서브셋 사용).

  • 부분 애플리케이션 재구성: GPT-6 Astra가 평균 이진 점수 84.3%로 가장 우수했고, Claude Opus 5(68.7%), GPT-5.6 Sol(60.7%)이 뒤를 이었다. 비용 대비 성능에서 항상 비용이 큰 모델이 우수한 것은 아니었다(예: Gemini 3.7 Flash가 GPT-5.3 Codex와 비슷한 성능을 훨씬 낮은 비용으로 달성).
  • 복원 깊이가 1에서 8로 증가할수록 성능이 크게 하락했다. Astra는 깊이 1에서 100% 성공했지만 깊이 8에서는 64.0%로, Opus 5와 Sol은 96%/92%에서 각각 32.0%로 급락했다.
  • 트레잭토리 분석 결과, 복원 깊이가 커질수록 필요한 코드 라인과 동작 검증 부담은 각각 9.3배, 10.7배 증가하는 반면, 목표당 관찰(observe) 노력은 오히려 크게(약 75%) 줄어드는 불균형이 나타났다. Astra는 관찰 활동이 가장 많으면서도 편집(edit) 단계는 가장 적은 "관찰 집약적" 전략으로 최고 성능을 냈다.
  • 참조 애플리케이션 소스에 직접 접근하려는 "우회 시도"(Git 히스토리, 공개 소스 조회 등)가 전체 궤적의 7.2%에서 발견되었으며 모델별 편차가 컸다(Grok 4.6 19.0% vs. Astra 0.3%).
  • 전체 애플리케이션 재구성: 12개 애플리케이션에서 GPT-6 Astra가 원자적 동작 복원 58.98%, 누적 워크플로 복원 49.15%로 최고를 기록했고, Opus 5(42.03%/28.81%), Sol(33.39%/21.07%)이 뒤를 이었다. 실패 원인 분석에서는 "참조에서 아예 관찰되지 않음"이 59.2%로 가장 큰 원인이었고, 나머지는 관찰했지만 미구현, 잘못된 표현형으로 구현, 잘못된 상태/결과로 구현 등이었다. 에이전트의 자체 검증이 정작 실패가 드러나는 워크플로를 재확인하지 않아 오류를 놓치는 패턴도 확인되었다.

한계점

현재 에이전트는 시각적 스크린샷 없이 구조화된 브라우저 관찰(텍스트, 접근성 정보, 상호작용 요소)만 받으므로, 시각적으로 grounded된 상호작용이나 시각적 충실도 평가는 다루지 않는다. 실험 범위도 자체 완결형 웹 애플리케이션에 국한되어 있어, 외부 서비스 연동, 비결정적 상태, 데스크톱/모바일 애플리케이션으로의 확장은 향후 과제로 남아 있다. 벤치마크 구축 자체가 GPT-5.6 Sol이라는 단일 모델에 의존하므로 채굴·마스킹·과제 생성의 품질이 구축 모델의 능력에 좌우될 수 있다. 또한 브라우저·에이전트 인프라(선택자 안정성, 관찰 품질)에 따라 채굴 가능한 동작의 범위와 측정 성능이 달라질 수 있다. 저자들은 참조 기반 소프트웨어 공학 기법이 허가받지 않은 상용 애플리케이션 복제(오용)에 악용될 가능성도 명시하며, 본 연구는 공개/오픈소스 저장소 기반의 자체 완결형 애플리케이션에 한정했다고 밝힌다.

시사점

ProgramDistill은 "실행 가능한 소프트웨어" 자체가 평가 대상일 뿐 아니라 사양(specification), 과제, 검증기, 학습 신호의 확장 가능한 원천이 될 수 있음을 보여준다. 복원 깊이라는 통제 가능한 난이도 축은 향후 궤적 증류(trajectory distillation)나 강화학습을 통한 커리큘럼 기반 코딩 에이전트 학습의 자연스러운 토대가 될 수 있다. 또한 관찰-검증-편집 간 노력 배분이 구현 능력 못지않게 중요한 성능 결정 요인이라는 발견은, 향후 코딩 에이전트 설계 시 단순한 코드 생성 능력뿐 아니라 정보 탐색 전략 자체를 개선 대상으로 삼아야 함을 시사한다.
