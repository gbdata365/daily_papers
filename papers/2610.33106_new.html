VibeGame: Prompt-to-Game Development with AI-Native Engine and Self-Evolving Adversarial Agent Team

바이브게임: AI 네이티브 엔진과 자가진화형 적대적 에이전트 팀을 이용한 프롬프트-투-게임 개발

VibeGame은 자연어 프롬프트(와 선택적 참조 이미지)만으로 완전히 플레이 가능한 2D 게임 프로젝트를 만들어내는 프레임워크로, AI가 직접 다루기 쉬운 게임 엔진과 8개 역할로 구성된 적대적 에이전트 팀, 그리고 학습 없이 경험을 재사용하는 자가진화 메커니즘을 결합해 기존 코딩 에이전트 하네스들보다 뛰어난 게임 품질을 달성한다.

한 줄 요약

VibeGame은 자연어 프롬프트(와 선택적 참조 이미지)만으로 완전히 플레이 가능한 2D 게임 프로젝트를 만들어내는 프레임워크로, AI가 직접 다루기 쉬운 게임 엔진과 8개 역할로 구성된 적대적 에이전트 팀, 그리고 학습 없이 경험을 재사용하는 자가진화 메커니즘을 결합해 기존 코딩 에이전트 하네스들보다 뛰어난 게임 품질을 달성한다.

배경 및 문제의식

게임 개발은 실시간 상호작용성, 일관된 비주얼 아이덴티티, 균형 잡힌 규칙을 동시에 요구하는 대표적인 고난도 소프트웨어 작업으로, 전통적으로 Unity, Unreal Engine, Godot 같은 엔진을 활용한 디자이너·프로그래머·아티스트의 장기간 협업이 필요했다. 이는 많은 창작자에게 진입 장벽으로 작용한다.

최근 AI가 이 장벽을 낮추려는 시도가 있었지만 두 방향 모두 한계가 있었다. Genie와 같은 월드 모델은 영상으로부터 바로 상호작용 경험을 생성하지만 편집 가능한 소스 코드를 만들지 못하며, DreamGarden처럼 상용 엔진(Unreal)에 LLM을 결합한 방식은 프로젝트 상태가 그래픽 인터페이스와 바이너리 자산에 흩어져 있어 에이전트가 이를 일관되게 점검·수정하기 어렵다. 한편 Claude Code, Codex 등 LLM 코딩 에이전트가 가능하게 한 "바이브 코딩(vibe coding)"을 게임에 확장한 "Prompt-to-Game(P2G)" 과제—자연어 설명(과 선택적 참조 이미지)만으로 완전한 플레이 가능 게임 프로젝트를 생성하는 것—가 다음 단계로 제시된다.

AutoUE, OpenGame 같은 선행 시스템과 GameDevBench, GameCraft-Bench 같은 벤치마크가 이 방향으로 진전을 이뤘으나, 대부분 런타임 검증을 최종 평가 단계에만 두거나 "빌드와 실행 성공 여부" 확인에 그친다. 그러나 많은 게임 문제는 실제 플레이 중에만 드러나며, 하나의 산출물을 수정하면 코드·씬·에셋·애니메이션·물리·설정 등 상호의존적인 요소 전반에 비일관성이 생길 수 있다. 저자들은 이를 해결하기 위해 (1) 에이전트가 직접 다룰 수 있는 프로젝트 상태 표현, (2) 상호작용에 기반한 실행 검증, (3) 검증된 개발 경험의 보존이라는 세 가지 결합된 역량이 필요하다고 본다.

핵심 기여

  • VibeGame 프레임워크 제안: 자연어 프롬프트를 완전하고 플레이 가능한 게임 프로젝트로 변환하며, 빠른 생성뿐 아니라 이후의 반복적 수정까지 지원한다.
  • AI-네이티브 게임 엔진: 코딩 에이전트가 그래픽 에디터 없이 프로젝트 상태를 직접 점검·수정하고 런타임 실행을 제어할 수 있게 하는 엔진을 설계했다. 이를 기반으로 구현과 검토를 분리하는 적대적 에이전트 팀(Adversarial Agent Team, AAT)과, 검증된 개발 경험을 재사용 가능한 지식으로 증류하는 학습 없는(training-free) 자가진화 메커니즘을 도입했다.
  • 포괄적 실증 평가: P2G와 PA2G(prompt-assets-to-game, 에셋 라이브러리가 주어지는 설정) 두 시나리오에서 여러 주류 에이전트 하네스와 비교해 우수한 성능을 입증했다.

방법론

VibeGame은 자연어 요청과 선택적 참조 이미지를 입력으로 받아, 실행·점검·수정이 가능한 완전한 2D 게임 프로젝트를 만든다. 전체 구조는 세 요소로 구성된다.

1) AI-네이티브 게임 엔진 (3.1절) Phaser(텍스트로 완전히 표현되는 웹 2D 프레임워크) 위에 구축하며, 에이전트 친화성을 위해 세 가지 속성을 정의한다. - GUI-Independent: 프로젝트 전체를 스키마가 검증되는 JSON 파일로 표현한다. 각 씬은 노드(시각적 외형, 충돌 형태, 행동 스크립트, 설정을 하나로 묶은 단위)의 계층 구조이며, 씬 간 공유 노드는 별도 정의 파일로 관리된다. 이 씬-노드-에셋 계층 구조 덕분에 누락된 에셋 참조 등 잘못된 의존관계를 실행 전에 스키마 검증으로 잡아낼 수 있다. - Runtime-Accessible: 프레임 동기(frame-synchronous) 방식의 프로그래밍 인터페이스로 실행을 일시정지·재개하거나 지정한 프레임 수만큼 진행시키고, 노드의 위치·속도 같은 런타임 속성을 점검·수정하며, "점프 누르기" 같은 의미 있는 행동을 주입하고 스크린샷을 캡처할 수 있다. - Source-Available: 엔진의 미컴파일 소스 코드 전체를 프로젝트 디렉터리에 복사해, 문서가 다루지 못하는 API나 구현 세부사항을 에이전트가 직접 확인할 수 있게 한다.

2) 적대적 에이전트 팀 (AAT, 3.2절) 오케스트레이터, 디자이너, 아티스트, 아키텍트, 프로그래머, 오디터(auditor), 플레이어, 리뷰어의 8개 전문 역할로 구성되며, 세 단계로 개발을 진행한다. - 의도 정렬(Intention Alignment): 디자이너가 간단한 요청을 게임 디자인 문서(GDD)로 확장하고, 아티스트가 이미지 생성 모델로 컨셉 아트를 만들어 사용자 확인을 받는다. - 병렬 개발(Parallel Development): 코드 워크플로우는 아키텍트(계획)→프로그래머(구현)→오디터(정적 검사)→플레이어(런타임 플레이 테스트 및 비전 모델을 통한 비주얼 검증)의 파이프라인으로 진행되며, 정적 검증과 런타임 플레이 테스트를 모두 통과해야 서브태스크가 완료된다. 아티스트 워크플로우는 GPT-Image-2, Nano Banana Pro 같은 이미지 생성 모델로 에셋을 만들고 배경 제거·크기 정규화 등 후처리를 거쳐 엔진에 등록한다. - 적대적 교정(Adversarial Correction): 독립적인 리뷰어가 기능성, 비주얼 품질, 플레이 가능성 기준으로 전체 프로젝트를 평가하고, 기준 미달 시 구체적 이유와 함께 반려하여 수정 작업이 반복된다.

3) 학습 없는 자가진화 (3.3절) 승인된 프로젝트로부터 재사용 가능한 경험을 세 가지 형태로 증류한다. - 스켈레톤(Skeletons): 특정 게임 유형의 재실행 가능한 프로젝트 템플릿으로, 프로젝트별 에셋은 제거하되 코드 구조·튜닝값·씬 흐름은 보존하며, 오류 노트와 아트 팩(에셋 생성 프롬프트, 후처리 규칙)을 포함한다. - 모듈(Modules): 여러 게임 유형에 재사용 가능한 노드 부착형 행동 스크립트로, 과거 실행 오류를 정적 검증 규칙으로 변환하는 자체 점검 로직을 포함할 수 있다. - 계약(Contracts): 반복되는 기능(예: 맵 구현)에 대해 디자이너·프로그래머·아티스트·오디터·플레이어 각 역할의 입력·출력·의존성·검증 기준을 규정한 문서로, 일반적인 빌드-리뷰 루프보다 검증된 절차를 통해 협업하도록 돕는다.

실험 설정 및 결과

설정: GameCraft-Bench의 15개 게임 유형에서 각 2개씩, 총 30개 과제를 샘플링해 Phaser에 맞게 엔진만 조정한 테스트셋을 구성했다. 모든 하네스에 과제당 24시간 예산과 xhigh 추론 강도를 부여했으며, P2G 설정에서는 네이티브 이미지 생성이 없는 하네스에도 VibeGame과 동일한 이미지 생성 모델을 제공했다. 판정 모델로는 GameCraft-Bench 기본 판정 모델(GPT-5.5)의 오류가 많아 GPT-6.1-Sol을 사용했다.

주요 결과(Table 1): 동일 기반 모델 조건에서, PA2G 설정의 일반 코딩 에이전트들은 서로 큰 차이가 없었고(최대 2.50점), GPT-5.6-Luna 기반에서는 이미지 생성 기능이 시각적 우위로 이어지지 않았다. 게임 개발 특화 시스템인 OpenGame도 일반 코딩 에이전트를 능가하지 못했다. 반면 VibeGame은 GPT-5.6-Luna 기준 4개 평가 범주(핵심 메카닉 M, 콘텐츠 깊이 D, 기능적 비주얼 V, 아트·표현 A) 모두에서 1위를 차지했고 최강 베이스라인보다 전체 점수 11.70점 높았다. 프런티어 모델 GPT-6.1-Sol 기준으로는 Codex(P2G)에 핵심 메카닉·기능적 비주얼에서 근소하게(1점 이내) 못 미쳤지만 콘텐츠 깊이(+4.76점)와 아트·표현(+7.72점)에서 크게 앞서, 전체 점수는 4.19점 높았다. 15개 게임 유형 중 13개에서 각 모델의 최강 베이스라인을 능가했다.

사용자 연구: 다양한 배경의 참가자 30명을 대상으로 VibeGame과 5개의 GPT-6.1-Sol 베이스라인을 쌍대 비교(150쌍, 평가 300건)한 결과, GPT-6.1-Sol 판정과 인간 평가 모두에서 VibeGame이 모든 베이스라인·모든 평가 범주에서 승리했으며, 평균 전체 승률은 72.7%였다.

애블레이션(Table 2, GPT-5.6-Luna 기준 10개 과제): AI-네이티브 엔진을 제거(w/o Engine)하면 전체 점수가 10.33점 하락했고, 적대적 리뷰 역할(오디터·플레이어·리뷰어)을 제거(w/o AAT)하면 4.63점 하락했다. 반대로 GPT-6.1-Sol로 증류한 경험을 GPT-5.6-Luna에 추가(w/ Experience)하자 전체 점수가 2.92점 상승해, 강한 모델에서 얻은 경험이 약한 모델로 전이될 수 있음을 보였다. 또한 엔진만 Codex(GPT-6.1-Sol)에 추가해도 2.69점 상승했다.

질적 분석: 스케이트보드 파크, 복싱 체육관 등의 사례에서 VibeGame은 일관된 비주얼 스타일과 완성도 있는 애니메이션(공중 트릭, 공격 전조 동작 등)을 보여준 반면, 비교 대상 Codex(PA2G/P2G)는 프로그래밍적 도형으로 캐릭터를 표현하거나 UI가 캐릭터와 겹치는 등의 결함을 보였다.

한계점

저자들이 명시한 한계는 두 가지다. 첫째, 2D 게임에 초점을 맞추었으며 더 복잡한 3D 장면이나 장기간 플레이를 지탱하는 완전한 상업용 게임 개발에는 아직 검증되지 않았다. 둘째, AI-네이티브 설계 원칙이 웹 기반 2D 엔진(Phaser) 위에 구현되어 있어, Godot 같은 기존 범용 엔진으로 확장해 에이전트가 기존 게임 프로젝트도 다룰 수 있게 하는 것은 향후 과제로 남아 있다.

시사점

이 연구는 "바이브 코딩"의 원칙(자연어 지시, 반복적 피드백)을 게임이라는 복합적 산출물로 확장하려면 단순히 코드 생성 능력을 높이는 것만으로는 부족하며, (1) 코드·씬·에셋·물리 등 상호의존적 요소를 명시적으로 드러내는 에이전트 친화적 프로젝트 표현, (2) 실행을 멈추고 들여다볼 수 있는 런타임 제어, (3) 검증된 경험을 다음 프로젝트로 전달하는 메커니즘이 함께 필요함을 보여준다. 애블레이션 결과는 엔진 구조와 적대적 리뷰 중 어느 한쪽만으로는 충분하지 않고 둘이 결합되어야 효과가 크다는 점을, 그리고 경험의 모델 간 전이 가능성은 비용이 큰 프런티어 모델의 개발 노하우를 더 저렴한 모델에 이식할 수 있는 실용적 경로를 제시한다. 다만 결과가 2D·단일 엔진(Phaser) 환경에 국한되어 있어, 3D 게임이나 기존 상용 엔진(Unity, Unreal, Godot 등)에 이 설계 원칙이 그대로 통할지는 추가 검증이 필요한 과제로 남는다.
