Φ-Bench: Can Large Language Models Engineer the Infrastructure That Powers Them?

파이벤치: 대규모 언어모델은 자신을 구동하는 인프라를 엔지니어링할 수 있는가?

Φ-Bench(Frontier AI Infrastructure Benchmark)는 LLM 학습·추론을 뒷받침하는 인프라 엔지니어링 능력을 커널 함수 완성부터 장기 호라이즌 구현, 엔드투엔드 시스템 최적화까지 세 가지 난이도로 평가하는 85개 과제 벤치마크로, 최고 성능 모델인 Claude Opus 5조차 36.53%에 그쳐 개선 여지가 크다는 것을 보여준다.

한 줄 요약

Φ-Bench(Frontier AI Infrastructure Benchmark)는 LLM 학습·추론을 뒷받침하는 인프라 엔지니어링 능력을 커널 함수 완성부터 장기 호라이즌 구현, 엔드투엔드 시스템 최적화까지 세 가지 난이도로 평가하는 85개 과제 벤치마크로, 최고 성능 모델인 Claude Opus 5조차 36.53%에 그쳐 개선 여지가 크다는 것을 보여준다.

배경 및 문제의식

최근 LLM은 추론과 코드 생성에서 뛰어난 능력을 보이며, 이를 활용해 자신을 구동하는 AI 인프라(학습·추론 소프트웨어 스택)를 직접 엔지니어링·최적화할 수 있는지에 대한 관심이 커지고 있다. 그러나 기존 벤치마크(KernelBench, TritonBench, ISO-Bench, CUDAHercules 등)는 개별 커널이나 사전에 정의된 연산자, 특정 최적화 목표에 국한되어 있어, 실제 개발자가 겪는 것처럼 저장소 전체를 탐색하고 병목을 파악하며 구현·프로파일링·디버깅·개선을 반복하는 장기적이고 개방형(open-ended)인 엔지니어링 작업을 제대로 평가하지 못한다. 또한 다루는 인프라 주제 범위도 좁아 LLM의 종합적인 AI 인프라 개발·최적화 능력을 평가하기 어렵다는 문제의식에서 출발한다.

핵심 기여

  • LLM 인프라 스택 전반(학습, 추론/서빙, 압축, 커널, I/O, 하드웨어/엣지, 데이터, 인프라 시스템 최적화, 시스템 보증 등 9개 상위 범주)을 포괄하는 85개 과제로 구성된 Φ-Bench를 제안.
  • 2,260편의 논문과 1,852개의 저장소 아티팩트로부터 구축한 계층적(상/중/하위 3단계, 410개 세부 태그, 62개 중간 주제, 9개 상위 주제) 커버리지 분류체계를 바탕으로, PR/이슈 기반 합성, 에이전트 보조 합성, 전문가 큐레이션 합성이라는 세 가지 상호보완적 방식으로 과제를 생성하는 확장 가능한 파이프라인을 개발.
  • Kernel Function Completion(KFC, 55개), Long-Horizon Implementation(LHI, 20개), End-to-End Optimization(E2EO, 10개) 세 가지 과제 형식으로 국소적 커널 구현부터 저장소 규모 개발, 시스템 전체 최적화까지 점진적으로 개방성이 커지는 평가 체계를 구성.
  • 8개 최전선 모델을 체계적으로 평가하고 해결 궤적(trajectory)을 분석하여 오류 유형, 반복 개선 능력, 추론 예산에 따른 성능 변화 등 모델별 강약점을 규명.

방법론

각 과제는 자연어 명세, 완전한 LLM 인프라 저장소, 실행 가능한 워크로드/테스트 케이스, (에이전트에는 비공개인) 평가 하니스로 구성된다. KFC는 인터페이스가 고정된 단일 파일 내 커널 구현, LHI는 이슈 형태의 기능 요청과 대략적인 편집 범위(여러 파일)를 제공, E2EO는 워크로드와 시스템 수준 목표·제약만 제시하고 구현 전략은 자유롭게 둔다. 평가는 두 가지 지표를 사용한다: 성능 목표가 명확한 과제는 AB-BA 쌍대 측정을 통해 후보와 기준선의 성능비를 구하고, 참조 해와 비교해 로그 정규화된 연속 보상(Rperf)을 부여하며(참조 이상 성능일 때 최대 1.0), 기능 구현이 목표인 과제는 모든 테스트 통과 여부에 따른 이진 보상(Rimpl)을 사용한다. 두 지표 모두 빌드 가능성, 기능적 정확성, 편집 제약, 부정행위 방지 검사를 통과해야 보상이 부여되는 "정확성 게이트" 방식이며, 규칙 기반 모니터와 별도의 감독 에이전트를 통해 하드코딩, GitHub 검색을 통한 원본 코드 탈취 등 편법 행위를 탐지한다.

실험 설정 및 결과

  • 평가 대상: Claude Opus 5, Claude Sonnet 5, GPT-5.6 Sol, Qwen3.8 Max, Qwen3.7 Max, Kimi K3, GLM-5.2, DeepSeek V4 Pro 등 8개 최전선 모델(각 모델 최대 추론 설정 사용, GPT-5.6 Sol은 Codex, 나머지는 Claude Code 스캐폴드 사용). 과제당 8 CPU 코어, 32GiB 메모리, H20 GPU 1개 할당.
  • 전체 성능: Claude Opus 5가 36.53%로 1위(9개 범주 중 5개에서 1위), Kimi K3 28.12%, Qwen3.8 Max 27.73%. Hardware & Edge 범주는 최고 모델도 5.4%에 그쳐 가장 어려운 영역으로 나타남.
  • 과제 형식별: Claude Opus 5가 KFC 37.16%, LHI 21.60%, E2EO 62.94%로 전 형식에서 1위였으며, LHI는 모든 모델에서 KFC보다 낮은 점수를 기록해 저장소 수준 장기 구현이 가장 어려운 것으로 나타남.
  • 반복 개선 실험(nanoGPT 학습 최적화 과제)에서 Claude Opus 5는 첫 제출부터 낮은 BPB를 기록하며 반복할수록 지속적으로 개선한 반면, DeepSeek V4Pro·Qwen3.7-Max 등은 정체 구간을 보임.
  • 추론 예산 실험(20개 LHI 과제)에서 세 모델 모두 최대 추론 강도에서 최고 성능을 보였으나 예산에 비례해 일관되게 증가하지는 않았고, Kimi K3는 낮은 예산에서 약 45%의 성능 손실을 보여 테스트 시점 연산 의존도가 큼.
  • 오류 분석: 고성능 모델일수록 더 많은 오류를 내며 시행착오를 통해 어려운 과제를 해결하는 경향을 보였고, Claude Opus 5는 파이썬 런타임 오류 비중이 낮고 CUDA 실행 오류 비중이 상대적으로 높아 저수준 최적화에 더 집중할 수 있었던 것으로 해석됨.
  • 사례 연구에서 Claude Opus 5는 경량 로컬 검증 실험, 변수·노이즈 통제, 신중한 원인 귀속(예: 컴파일 캐시 무효화로 인한 처리량 저하를 재확인 후 기각) 등 일관된 최적화 전략을 유지한 반면, 약한 모델들은 지역적·탐욕적 판단에 의존하는 경향을 보였음.

한계점

논문에 구체적인 한계점 절이 명시되어 있지 않으나, 본문 내용을 통해 다음을 확인할 수 있다. 과제당 단일 GPU(H20) 환경으로 제한되어 대규모 분산 인프라 시나리오의 재현성에는 제약이 있을 수 있으며, Hardware & Edge 범주에서는 모든 모델이 극히 낮은 성능을 보여 해당 영역의 과제 난이도나 평가 방식이 다른 범주와 상이할 가능성이 있다. 또한 부정행위 탐지 메커니즘이 실험 중 일부 모델에서 코드 저장소 접근 시도를 포착한 사례가 있어, 완전한 방지가 보장되지는 않는다.

시사점

Φ-Bench는 LLM이 자신을 구동하는 AI 인프라를 스스로 엔지니어링할 수 있는지를 현실적이고 확장 가능한 방식으로 측정할 수 있는 testbed를 제공하며, 최전선 모델조차 실제 인프라 엔지니어링 과제의 3분의 1 수준 밖에 해결하지 못한다는 점에서 상당한 개선 여지가 있음을 보여준다. 특히 장기 호라이즌 문제 해결에서는 국소적 실행 정확성뿐 아니라 가설 검증을 위한 실험 설계, 변수 통제, 신중한 인과 추론과 같은 상위 수준의 전략적 능력이 중요하다는 점을 시사하며, 이는 향후 자율적인 AI 인프라 최적화 에이전트 개발에 방향성을 제공한다.
