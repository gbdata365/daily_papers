SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

SoL-Pi: 효율적인 에이전트 하네스를 위한 자동 연구 루프의 재귀적 스케일링

한 줄 요약

AI 연구 에이전트가 스스로 코딩 에이전트의 "하네스(harness, 실행 프레임워크)"를 반복적으로 개선하도록 만들어, 성능은 거의 유지하면서 토큰 사용량을 약 45~49%, API 비용을 약 1/3 절감하는 SoL-Pi 시스템을 제안한다.

배경 및 문제의식

최근 코딩 에이전트는 사람의 감독 없이 장시간 자율적으로 작업을 수행하는 방향으로 발전하고 있으며, 이 과정에서 추론, 도구 사용, 피드백으로 이어지는 실행 궤적(trajectory)이 매우 길어진다. 궤적이 길어질수록 토큰 사용 효율이 시스템 차원의 핵심 문제로 떠오르는데, 기존 연구는 주로 더 빠른 어텐션 커널, 서빙 인프라, 양자화 같은 모델 압축, 혹은 더 저렴한 모델 사용 등 "모델·인프라 레벨"의 비용 절감에 집중해 왔다.

이 논문은 이와 직교하는 방향, 즉 모델과 환경 사이를 중개하는 "에이전트 하네스" 자체를 최적화하는 방법을 탐구한다. 문제는 하네스 최적화가 도구 사용, 컨텍스트 관리, 검증, 위임, 복구, 종료 등이 서로 강하게 얽혀 있어 사람이 직접 긴 실행 로그를 분석하고 원인을 찾아 코드를 수정하는 방식으로는 확장하기 어렵다는 점이다. 또한 선행 연구(Meta-Harness, RHI 등)는 하네스를 자동으로 탐색·개선하는 시도를 보여주었지만, 최근 연구에서는 탐색에 사용한 태스크에 하네스가 과적합되어 미공개(held-out) 태스크에서는 개선 효과가 미미해질 수 있다는 문제가 지적되었다.

핵심 기여

  • 재귀적 자기개선(RSI, Recursive Self-Improvement)에서 영감을 받아, AI 연구 에이전트가 실행 궤적을 관찰하고 하네스 개선안을 제안·검증·채택하는 자동 연구 루프(Auto-Research Loop) 구조인 SoL-Pi를 제안했다.
  • 탐색(search)과 최종 검증(held-out evaluation)을 철저히 분리하는 원칙(폭과 깊이, 독립적 검증, 확장 가능한 오케스트레이션)을 설계하여, 탐색 과정에서 발견한 개선안이 특정 태스크에 과적합되지 않고 새로운 벤치마크·모델로 전이(transfer)되도록 했다.
  • 약 150개의 제안 방향과 약 500개의 실행 가능한 환경, 3,000회 이상의 실행, 60,000회 이상의 에이전트-환경 상호작용 규모로 탐색을 수행하여, 최종적으로 4가지 재사용 가능한 하네스 메커니즘(Action Fusion, Online Context Compact, ObservationPack, Evidence-Preserving Reducer)을 도출했다.
  • 이 4가지 메커니즘을 결합한 SoL-Pi 하네스가 EdgeBench에서 기존 Pi 하네스 대비 성능은 93.7~94.3% 수준으로 유지하면서 토큰 트래픽을 44.7~49.0%, API 비용을 약 1/3 절감함을 보였고, 탐색에 쓰지 않은 모델(Opus 5)로도 추가 튜닝 없이 효과가 이전됨을 확인했다.

방법론

SoL-Pi의 탐색 파이프라인은 하네스 개선을 "재사용 가능한 효율화 메커니즘을 찾는 RSI 스타일 탐색"으로 정식화한다. 연구 에이전트가 기존 하네스의 실행 궤적을 분석해 반복되는 낭비 요인을 찾고, 후보 개선안 풀(idea pool)을 만든 뒤 개발 환경에서 효과를 검증한다. 채택 기준은 두 단계 게이트로 구성된다: (1) 사전에 고정한 능력(capability) 지표가 허용 오차 내에 있어야 하고, (2) 사전에 선언한 효율성 지표 중 최소 하나를 개선해야 한다. 이 지표와 허용 오차는 최적화 에이전트가 임의로 바꿀 수 없도록 고정되어, 에이전트가 평가 기준 자체를 악용(게이밍)하지 못하게 막는다.

탐색은 "넓고 얕은" 외부 단계와 "좁고 깊은" 내부 단계로 나뉜다. 외부 단계는 컨텍스트, 진행 관리, 도구, 위임, 프롬프트·정책, 개선·평가라는 6개 범주에 걸쳐 152개의 제안 방향에서 시작하며, 각 방향은 구체적인 낭비 원인과 이를 해결할 하네스 변경안을 제시해야 한다. 내부 단계는 Ralph Loop 기반의 반복적 구현 루프를 사용해 제안→구현→고정된 실험→결과 검토→채택/수정/폐기의 사이클을 반복하고, 독립적인 리뷰어가 후보를 검토한다.

탐색 환경은 두 종류로 구성된다: (1) GitHub 이슈-PR 쌍에서 파생된 495개의 저장소 기반 환경(패치 적용 전 실패·적용 후 통과하는 회귀 테스트를 보유), (2) 실행 가능한 검증기를 먼저 설계하고 그에 맞춰 태스크 환경을 구성하는 40개의 합성 환경(Terminal-Bench-2 스타일). 최종 검증에 사용하는 EdgeBench(공개된 51개 태스크)는 탐색 과정에서 완전히 격리되며, 후보가 동결(freeze)된 이후에만 사용되고 그 결과는 다시 탐색에 피드백되지 않는다.

이 과정에서 채택된 4가지 메커니즘은 다음과 같다. - Action Fusion: 파일 수정과 뒤이은 테스트/빌드/실행 명령을 하나의 도구 호출로 합쳐, 중간에 모델을 한 번 왕복하는 비용을 없앤다. - Online Context Compact: 계획 단계(plan step) 완료 시점마다 남은 요청 수를 추정하고, 컨텍스트 압축으로 얻는 절감량이 프롬프트 캐시 재작성 비용보다 클 때만 압축을 수행하는 비용 게이트를 둔다. - ObservationPack: 10KiB를 넘는 큰 도구 출력 결과를 로컬에 보관해두고, 처음 두 번의 모델 요청까지는 전체 결과를 보내지만 세 번째 요청부터는 안정적인 핸들과 앞뒤 발췌본(약 1KB)으로 대체하며, 필요 시 정확한 원본을 다시 불러올 수 있게 한다. - Evidence-Preserving Reducer: 4KiB 이상의 빌드/테스트 로그를 저비용 모델을 이용해 핵심 근거만 담은 요약본(receipt)으로 압축하고, 결정론적 검증기가 스키마·해시·정확한 인용문 등을 검증해 실패 시 원본으로 되돌아간다.

네 메커니즘은 각각 행동 실행, 컨텍스트 관리, 관찰(observation) 저장, 위임된 읽기(delegated reading)라는 서로 다른 단계를 담당하도록 설계되어 상호 보완적으로 작동한다. 모든 메커니즘은 오픈소스 하네스 Pi의 확장으로 구현되었으며, Evidence-Preserving Reducer는 GPT-5.6 Luna(high) 모델을 근거 추출용 보조 모델로 사용한다.

실험 설정 및 결과

주 평가는 EdgeBench(공개 51개 태스크, GPT-5.6 Sol/Claude Opus 5 백엔드)에서 수행되었으며, Codex, OpenSquilla, Oh-My-Pi, OpenCode, Oh-My-Opencode, Pi 등 다양한 네이티브/서드파티 하네스와 비교했다. - GPT-5.6 Sol 백엔드에서 SoL-PiEfficiency는 토큰 트래픽 1.10B(Pi 대비 49.0% 감소), API 비용 $894(Pi $1,339 대비 약 33% 감소), 평균 점수 42.0(Pi 44.8의 93.7% 수준)을 기록했다. - 단일 메커니즘 중 성능이 가장 높은 조합인 SoL-PiPerformance는 평균 점수를 44.8→47.2(+5.3%)로 오히려 높이면서 토큰 트래픽도 6.1% 줄였다. - 탐색에 쓰이지 않은 Opus 5 백엔드로 추가 튜닝 없이 전이했을 때도 SoL-Pi[Efficiency]는 Pi 대비 점수의 94.3%를 유지하면서 토큰 트래픽 44.7%, API 비용 33.5% 절감을 보여 메커니즘의 전이 가능성을 시사했다. - Terminal-Bench 4(63개 CPU 태스크)와 IMO 2026(6문제, Lean 4 검증)에서도 SoL-Pi는 Codex·Pi 대비 해결한 태스크 수는 비슷하거나 약간 낮지만(Terminal-Bench 4: 15/63 vs Codex·Pi 18/63) 총비용과 해결 태스크당 비용은 더 낮았고(IMO 2026: 6문제 중 3문제 통과, 통과 문제당 비용 $20.90로 최저), 효율성 개선이 EdgeBench 밖에서도 일반화됨을 보였다. - 20개의 SoL-Pi 워커로 구성된 커널 최적화 멀티에이전트 스웜 실험에서는 Pi 기반 스웜 대비 API 비용을 26.8% 절감하면서도 동일한 8개 속도 기준을 모두 통과했다(Pi 스웜은 1개 기준 미달). - 메커니즘별 단독 기여 분석(add-one 평가)에서는 모든 구성 요소가 두 백엔드 모두에서 총 토큰량을 줄였고, GPT-5.6 Sol에서는 ObservationPack이, Opus 5에서는 Action Fusion이 가장 높은 평균 점수를 기록했다. 다만 Opus 5에서는 메커니즘의 발동 빈도(trigger rate)와 발동 강도가 GPT-5.6 Sol보다 낮게 나타나, 하네스가 GPT-5.6 Sol 궤적에만 맞춰 최적화된 영향으로 해석되었다.

한계점

  • 저자들이 스스로 언급한 한계로, 하네스 아티팩트가 탐색에 쓰이지 않은 완전히 새로운 태스크·환경으로 일반화되는 정도는 여전히 지속적인 도전 과제이며, 이번 결과는 "예비적(preliminary)" 증거로 제시된다.
  • 현재 하네스는 단일 LLM(GPT-5.6 Sol)의 궤적만으로 학습되었고, 다른 백엔드(Opus 5)에서는 메커니즘의 발동 빈도와 강도가 더 낮게 나타나 다중 백엔드 학습(Multi-Backend Training)이 향후 과제로 남았다.
  • "재귀적 효율 개선(Recursive Efficient Improvement)"—더 효율적인 하네스로 다음 세대 탐색 비용 자체를 낮추는 복합 효과—은 아직 실증되지 않은 장기적 연구 비전으로만 제시되었다.
  • 완전한 자동 연구 루프를 실행하는 데 드는 연산 비용이 매우 커서, 탐색의 폭(breadth)과 깊이(depth)를 고정된 예산 아래 통제된 방식으로 비교하는 스케일링 법칙 분석은 향후 과제로 남겨두었다.
  • 컨텍스트 단축이 프롬프트 캐시 재사용률을 낮출 수 있다는 트레이드오프가 존재하며(캐시 쓰기 트래픽 증가), 이를 총비용 관점에서 관리해야 한다는 점도 논문에서 스스로 지적한 유의점이다.

시사점

이 논문은 모델 자체를 재학습하지 않고도 "에이전트를 둘러싼 하네스"를 자동으로 연구·개선함으로써 상당한 비용 절감이 가능함을 보여준다. 이는 향후 자율 코딩 에이전트, 멀티에이전트 스웜, 장시간 자율 연구 시스템을 운영할 때 모델 교체나 인프라 투자 없이도 하네스 개선만으로 비용 효율을 크게 높일 수 있는 실용적 경로를 제시한다. 또한 "탐색과 최종 검증의 엄격한 분리"라는 설계 원칙은 자동화된 시스템 최적화 연구 전반(단순히 에이전트 하네스뿐 아니라 프롬프트, 워크플로 등 다른 자동 설계 영역)에서 과적합을 방지하는 일반적인 방법론으로 참고할 만하다. 저자들은 이를 "하네스의 사전학습(pretraining the harness)"이라는 장기적 비전으로 연결하며, 더 많은 환경과 아이디어로 탐색을 확장하면 지속적인 개선이 가능하다는 가설을 제시한다.
