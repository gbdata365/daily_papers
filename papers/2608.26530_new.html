PILOT in the Loop: Live Self-Improvement for Long-Horizon Agents

PILOT 인 더 루프: 장기 호라이즌 에이전트를 위한 실시간 자기개선

작업이 끝난 뒤에야 경험을 반영하는 기존 자기개선 방식과 달리, 실행 중인 워커(worker)를 감독자(supervisor)가 실시간으로 관찰·개입하고 그 경험을 즉시 재사용 가능한 스킬/메모리로 기록하는 "supervisor-worker" 구조인 PILOT을 제안하여, 터미널/코드 수정 등 장기 호라이즌(long-horizon) 에이전트 과제에서 기존 하니스 대비 큰 폭의 성능 향상을 달성했다.

한 줄 요약

작업이 끝난 뒤에야 경험을 반영하는 기존 자기개선 방식과 달리, 실행 중인 워커(worker)를 감독자(supervisor)가 실시간으로 관찰·개입하고 그 경험을 즉시 재사용 가능한 스킬/메모리로 기록하는 "supervisor-worker" 구조인 PILOT을 제안하여, 터미널/코드 수정 등 장기 호라이즌(long-horizon) 에이전트 과제에서 기존 하니스 대비 큰 폭의 성능 향상을 달성했다.

배경 및 문제의식

장기 호라이즌 에이전트 작업은 진행 과정에서 재사용 가능한 절차(성공 사례)나 반복되는 실패 패턴(실패 사례) 같은 값진 경험을 만들어낸다. 하지만 Reflexion, ExpeL, 자기진화형 하니스(self-evolving harness) 같은 기존 자기개선 기법 대부분은 "post-hoc", 즉 실행이 완전히 끝난 뒤에야 궤적을 검토하고 하니스를 업데이트한다. 이 때문에 새로 얻은 교훈이 정작 그 교훈을 만들어낸 현재 실행을 구제하지도, 즉시 검증되지도 못하고 다음 별도 실행에서야 시험된다는 한계가 있다.

또한 저자들은 기존 에이전트 아키텍처가 "실시간 교정(live correction)"과 "전담 자기개선 역할"을 동시에 지원하지 못한다는 구조적 공백을 지적한다. 단일 에이전트의 자기 교정(ReAct, Self-Refine, CRITIC 등)은 실행과 진단을 같은 에이전트, 같은 컨텍스트 안에서 처리해야 하므로 주의가 분산된다. 반면 서브에이전트 위임 방식(AutoGen, MetaGPT, Magentic-One, Claude Code 등)은 실행과 메인 에이전트를 분리하지만, 메인 에이전트는 보통 서브에이전트가 완전히 끝난 뒤 최종 요약만 받을 뿐 실행 중인 서브에이전트를 실시간으로 유도할 수 없다.

핵심 기여

  1. 실시간 자기개선(live self-improvement)의 정식화: 현재 실행을 즉시 교정하는 동시에 지속형 하니스를 갱신하는 닫힌 루프(closed loop)로 자기개선 개념을 재정의했다.
  2. PILOT 제안: 실시간 조종(live steering)과 실시간 자기진화(live self-evolution)를 하나의 실행 경험 스트림 위에서 결합한 supervisor-worker 하니스를 설계했다.
  3. 광범위한 실험적 검증: 2개의 고정된(frozen) 백본 모델과 3개의 장기 호라이즌 벤치마크에서 성능뿐 아니라 작업 복구, 스킬 성장, 토큰 효율성까지 함께 분석했다.

방법론

PILOT은 기존 코딩 에이전트 런타임인 Pi를 확장하여 구현되었으며, 감독자(supervisor)는 하나의 에이전트 세션, 워커(worker)들은 같은 프로세스 내에서 별도로 스폰(spawn)되는 세션으로 동작한다. 실험에서는 동일한 고정 모델이 감독자와 워커 역할을 모두 수행한다(오케스트레이션 효과와 모델 능력 차이를 분리하기 위함).

핵심 구성 요소는 다음과 같다.

  • 역할과 지속 상태: 모델 파라미터 θ는 고정하고, 스킬 라이브러리 K와 메모리 M으로 구성된 지속형 하니스 H만 에피소드 간에 진화시킨다. 감독자는 하나 이상의 워커를 스폰하며, 각 워커는 현재 하니스 H를 로드하고 격리된 컨텍스트에서 궤적 ξ를 생성한다. 워커의 탐색 과정, 막다른 시도, 장황한 도구 출력은 기본적으로 각자의 격리된 컨텍스트에 남아 감독자의 컨텍스트를 오염시키지 않는다.

  • 양방향 실시간 채널(live steering): 감독자와 각 활성 워커는 실행 내내 연결된 채널을 유지하며 다섯 가지 작업을 지원한다.

  • Notification(워커→감독자): 워커가 진행 상황, 중간 결과, 위험 신호를 자발적으로 보고(실행은 계속됨).
  • Question(워커→감독자): 워커가 판단이 필요한 지점에서 질문하고 응답을 기다림.
  • Result(런타임 자동): 워커가 종료되면 최종 결과와 워커 인덱스가 감독자에게 자동 전달됨.
  • Steer(감독자→워커): 궤적이 잘못된 방향으로 가고 있다고 판단되면 감독자가 해당 워커의 다음 턴에 반영될 지침을 큐에 추가(현재 턴은 끝까지 진행).

  • Abort(감독자→워커): 더 이상 계속할 가치가 없는 워커 세션을 중단.

  • 실시간 자기진화(live self-evolution): 활성 실행 도중 감독자가 재사용 가능한 성공 절차, 프로젝트 관례, 반복되는 실패 패턴을 발견하면 즉시 스킬 라이브러리 K나 메모리 M에 기록하여 하니스를 H에서 H'로 갱신한다. 이후 스폰되는(같은 에피소드 내이든 이후 에피소드든) 모든 워커는 갱신된 H'를 로드함으로써 자기개선 루프가 닫힌다.

실험 설정 및 결과

벤치마크: Terminal-Bench 2.0(89개 실행 가능 과제, 셸 기반 시스템/엔지니어링 작업), SWE-bench Multilingual(파이썬 이외 언어로 확장된 저장소 수준 코드 수정), SWE-bench Pro(더 길고 어려운 저장소 이슈 수정).

백본: 오픈 웨이트 모델인 GLM-5.1과 Kimi-K2.6 두 종을 고정 백본으로 사용.

비교 하니스: Terminal-Bench 2.0에서는 Pi, OpenCode, Terminus-2, Hermes와 비교했고, SWE-bench 계열에서는 Pi, OpenCode, Mini-SWE-Agent, Hermes와 비교했다.

One-shot 설정 결과: 매 과제를 새 하니스 상태에서 시작해 실시간 조종의 효과만 측정한다. PILOT은 Terminal-Bench 2.0에서 GLM-5.1 71.9%(2위 OpenCode 대비 +5.0pt), Kimi-K2.6 71.3%(2위 Pi 대비 +4.4pt)를 기록했고, 어려운(Hard) 과제에서 두 백본 모두 55.0%로 최고치를 보였다. 6개 백본-벤치마크 조합 중 5개에서 1위를 차지했으며, SWE-bench Pro에서는 평균 59.9%로 최강 단일 에이전트 베이스라인인 Pi(55.5%)를 4.4pt 앞섰다.

자기개선(self-improvement) 설정 결과: Terminal-Bench 2.0 과제를 여러 iteration으로 묶어, 각 iteration이 공유 하니스 상태에서 시작하고 종료 후 성공한 실행에서 나온 스킬/메모리 갱신만 다음 iteration에 반영되도록 설계했다(벤치마크 채점 신호는 실행 중 전혀 제공되지 않음). 20회 iteration에 걸쳐: - 최고 관측 pass rate가 GLM-5.1은 66.3%→80.9%(+14.6pt), Kimi-K2.6은 68.5%→80.9%(+12.4pt) 상승. - 같은 초기 스킬 라이브러리에서 시작한 비교에서 PILOT은 +14.6pt 개선한 반면 OpenCode는 +7.9pt, Pi는 +2.3pt에 그침. - 스킬 라이브러리 크기가 GLM-5.1은 62→83개(+21), Kimi-K2.6은 50→81개(+31)로 증가. - 평가 과제당 평균 출력 토큰이 GLM-5.1 28.5K→16.3K(-42.9%), Kimi-K2.6 41.9K→22.1K(-47.4%)로 감소. - 백만 출력 토큰당 성공 평가 수(토큰 효율성)는 GLM-5.1 +110.3%, Kimi-K2.6 +134.0% 향상. - 성능 향상은 난이도가 높을수록 크게 나타났다(Hard 과제에서 GLM-5.1 +8개, Kimi-K2.6 +12개 추가 통과).

실시간 조종의 질적 분석: 성공한 실행 중 실시간 조종의 도움을 받은 비율은 Easy 과제에서는 0%였고 Hard 과제로 갈수록 증가(GLM-5.1 6.1%, Kimi-K2.6 19.7%, 전체 평균 각각 2.3%/10.6%)했다. 논문은 두 가지 대표 사례를 제시한다: (1) CoreWars 과제에서 감독자가 비생산적인 전략(합성 상대 대상 튜닝)을 중단시키고 검증된 공개 전략(Silk Warrior 1.3)으로 전환하도록 유도하여 성공, (2) Torch 텐서 병렬화 과제에서 감독자가 bias를 all_reduce 이전에 더해 world_size배로 중복 합산되는 구현 오류를 짚어주어 수정 후 13개 검증 테스트를 모두 통과.

한계점

  • 반복적 자기개선 평가는 동일 과제를 여러 iteration에 걸쳐 반복 실행해야 하므로 단일 추론 실행보다 비용이 훨씬 크며, 이 때문에 평가 범위가 3개 벤치마크와 2개 오픈 웨이트 백본으로 제한되었다. 더 넓은 범위의 벤치마크와 독점(proprietary) 모델에 대한 검증은 향후 과제로 남아 있다.
  • 실험에서는 감독자와 워커가 동일한 백본 모델을 공유하는데, 이는 실제 사용 시나리오를 반영하지만 서로 다른 모델을 조합했을 때(heterogeneous pairing) 감독 품질, 과제 성능, 비용 간의 트레이드오프는 탐구되지 않았다.

시사점

이 연구는 에이전트 자기개선이 "실행 종료 후 일괄 반영"이 아니라 "실행 중 교정과 지속적 축적이 하나로 연결된 루프"일 때 가장 효과적임을 보여준다. 즉 감독을 실행과 분리하되 완전히 단절시키지 않고 살아있는 채널로 유지함으로써, 현재 진행 중인 작업을 구제하는 동시에 그 경험을 후속 작업이 재사용할 수 있는 지식으로 즉시 전환할 수 있다. 이는 향후 코딩 에이전트, 서브에이전트 오케스트레이션, 하니스 자동 진화 연구에서 "실시간성(liveness)"을 설계 축으로 고려해야 함을 시사하며, 특히 실행 시간이 길고 오류가 누적되기 쉬운 어려운 과제일수록 감독자의 개입 가치가 커진다는 점은 향후 장기 호라이즌 에이전트 설계에 실질적인 지침을 제공한다.
