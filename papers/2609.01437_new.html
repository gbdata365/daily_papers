HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

하네스데브: LLM은 스스로 에이전트 하네스를 만들고 진화시킬 수 있는가?

에이전트의 실제 성능을 좌우하는 "하네스(harness, 모델 외부의 실행 인프라)"를 LLM이 스스로 만들고 지속적으로 개선할 수 있는지를 평가하는 벤치마크 HarnessDev를 제안하고, 6개 최신 모델을 대상으로 이를 검증한 결과 하네스를 처음부터 구축하는 능력은 영역별 편차가 크고, 피드백을 통한 지속적 개선(진화)은 불안정하며 다른 실행 모델로의 전이도 제한적임을 보였다.

한 줄 요약

에이전트의 실제 성능을 좌우하는 "하네스(harness, 모델 외부의 실행 인프라)"를 LLM이 스스로 만들고 지속적으로 개선할 수 있는지를 평가하는 벤치마크 HarnessDev를 제안하고, 6개 최신 모델을 대상으로 이를 검증한 결과 하네스를 처음부터 구축하는 능력은 영역별 편차가 크고, 피드백을 통한 지속적 개선(진화)은 불안정하며 다른 실행 모델로의 전이도 제한적임을 보였다.

배경 및 문제의식

에이전트가 연구 프로토타입에서 실제 배포되는 도구로 옮겨가면서, 그 성능은 모델 가중치 자체보다 그 외부의 실행 인프라, 즉 실행 루프·도구 사용·문맥 관리·실패 복구·결과 검증을 담당하는 "하네스"에 크게 좌우된다. 저자들은 동일한 GPT-5 가중치라도 Terminus 2에서는 Terminal-Bench 2.1의 35.2%를 풀지만 Codex CLI에서는 49.6%를 푼다는 사례를 들어 이 영향력을 보여준다. 그러나 기존 에이전트 평가는 대체로 하나의 하네스를 고정한 채 그 안에서의 과제 수행 성능만 보고할 뿐, 모델이 하네스 자체를 개발하는 능력은 상대적으로 탐구되지 않았다. 저자들은 이를 산업계의 "포워드 배치 엔지니어(FDE)" 역할에 비유하는데, FDE는 모호한 목표를 구체적 명세로 번역하고, 신뢰할 만한 피드백 신호를 스스로 구축하며, 미래 과제가 실행될 실행 시스템(도구, 문맥 관리, 상태, 검증 인터페이스)을 만들고 유지보수한다는 세 가지 구조적 과제를 안고 있다. HarnessDev는 이 중 세 번째 층, 즉 모델이 약한 출발점에서 실행 시스템을 스스로 만들고 피드백으로 개선할 수 있는지를 다룬다.

핵심 기여

  1. 평가 단위를 "과제 출력물"에서 "실행 가능한 인프라(하네스)"로 전환한 벤치마크 HarnessDev를 제안했다. 이는 Creation(하네스 구축)과 Evolution(하네스 진화)이라는 두 단계로 구성된다.
  2. Creation 단계에서는 약한 시드(seed) 하네스와 소수의 개발용 사례만으로 완전한 실행 시스템을 구축하는 능력을, Evolution 단계에서는 실행 피드백을 이용해 자신이 만든 하네스를 반복적으로 개선하는 능력을 측정하는 프로토콜을 설계했다.
  3. 생성된 하네스를 성능(held-out 벤치마크에서의 과제 성공률)과 효율성(실행 토큰 비용)이라는 두 축으로 평가하고, 개발자 모델(creator)과 실행자 모델(executor)을 분리해 하네스 자체의 이식성(portability)을 별도로 측정할 수 있는 Self-Eval/Unified-Eval 프로토콜을 마련했다.
  4. 6개 창작 LLM(Opus 4.8, GPT-5.5, Gemini 3.1 Pro, DeepSeek V4 Pro, Qwen 3.7 Max, Seed 2.0 Pro), 4개 도메인(코드, 데이터 분석, 글쓰기, 리서치), 5개 다운스트림 벤치마크(SWE-bench Pro, Terminal-Bench 2.1, MLE-bench, EQ-Bench3, BrowseComp), 총 2,207개의 고유 다운스트림 사례에 걸쳐 대규모 실증 결과를 제시했다.

방법론

HarnessDev는 창작 LLM(LC)이 개발 환경(D) 안에서 실행 가능한 하네스(H)를 만들고, 그 하네스가 동결(freeze)된 뒤 실행자 LLM(LE)이 그 위에서 다운스트림 과제를 수행하며, 평가자(J)가 결과를 채점하는 구조로 정의된다. Creation(RQ1)에서는 모든 창작자가 동일한 "약한 시드" 하네스 Hseed에서 출발한다. 이 시드는 실행 루프, 과제 분해, 도구 정책, 문맥 관리, 지속 상태, 검증기, 재시도 로직이 전혀 없는 순수한 호환 계층으로, 수정하지 않으면 모든 다운스트림 벤치마크에서 0점을 받는다. 창작자는 과제군 명세, 도구·권한 제약, 짧은 설계 튜토리얼, 1~3개의 개발용 사례만 받고 숨겨진 인간 구현이나 최종 평가셋은 볼 수 없다. Evolution(RQ2)에서는 창작자가 자신이 만든 RQ1 코드 하네스(H0)에서 출발해, 고정된 100개 SWE-Pro 과제와 89개 Terminal-Bench 과제로 구성된 피드백셋의 실행 결과를 받으며 반복 개선을 수행한다. 총 10개의 공식 평가 쌍(pair) 예산이 주어지며, 최종적으로 창작자가 선언한 버전은 개발 중 전혀 노출되지 않은 630개의 held-out SWE-Pro 인스턴스에서 추가로 평가된다.

평가는 두 축으로 이루어진다. 성능(capability)은 held-out 다운스트림 과제에서의 성공률로, 효율성(efficiency)은 동결된 하네스가 다운스트림 과제를 풀 때 소비하는 실행자 모델의 토큰 수로 측정한다. Self-Eval은 창작자 자신이 실행자 역할도 겸하는 설정이고, Unified-Eval은 모든 하네스를 동일한 고정 실행자(Gemini 3.1 Pro)로 실행해 하네스 간 직접 비교를 가능하게 한다. 또한 제출된 하네스가 과제별 정답을 하드코딩하거나 숨겨진 테스트·정답에 접근하는 등 부정행위를 하지 않는지, 실제 저장소 diff나 최종 환경 상태만을 채점 근거로 삼는 방식으로 감사(audit) 가능하게 설계했다.

실험 설정 및 결과

Creation 결과, Self-Eval 기준 Opus 4.8이 전체 평균 67.8점으로 가장 높았지만, 인간이 설계한 참조 시스템(86.2점)에는 못 미쳤다. 글쓰기(Writing) 영역은 인간 참조에 근접했고 머신러닝 실험(MLE-bench)에서는 Opus 4.8과 Gemini 3.1 Pro가 각각 32.9%, 32.4%의 메달률로 인간 참조(24.0%)를 오히려 능가했다. 반면 리서치(BrowseComp) 영역은 격차가 가장 컸고 코드(SWE-Pro, Terminal-Bench) 영역도 여전히 인간 참조에 크게 뒤처졌다. 데이터 분석 실패 과제의 77.8%가 하네스 결함에 기인한다고 분석되어, 병목이 실행자 모델의 능력만이 아니라 하네스 설계 자체에도 있음을 보였다. 실행자를 고정했을 때(Unified-Eval) 순위가 크게 바뀌었는데, 예를 들어 Opus의 Search 하네스는 실행자를 Gemini로 바꾸자 중복 질의율이 10.1%에서 88.2%로 치솟는 등, 하네스가 원래 만든 모델에 맞춰 최적화되어 있어 다른 모델로의 전이가 제한적임을 보여주었다. 코드 생성량과 성능은 비례하지 않았으며(Gemini는 가장 적은 코드로 최고 Terminal-Bench 점수를 얻음), 자체 테스트 개수보다 "피드백을 읽고 반영하는 수정 횟수"가 성능과 훨씬 강하게 상관되었다(스피어만 상관 0.57 vs 0.13~0.26).

Evolution 결과, 5개 창작자 모두 자신의 실행 환경(Self-runtime)에서는 가시적 피드백셋 점수가 개선되었지만, held-out 630개 과제에서의 개선폭은 훨씬 작아졌다(평균 +3.11점, 범위 +1.43~+4.44점). 실행자를 Gemini로 고정한 경우에는 오직 Opus만 held-out에서 개선되었고 나머지 세 계열은 오히려 퇴보했다. 64회의 공식 버전 전환 중 8회는 두 벤치마크 모두에서 퇴보했고, 27회는 반복 실행 잡음 범위 안의 미미한 개선에 불과했으며, 명확한 긍정적 개선은 단 2회였다. 가시적 피드백 점수와 held-out 점수는 같은 방향으로 움직인 경우가 64회 중 34회(53.1%)에 불과했고, 9개 계열 중 단 2개만이 held-out 최적 버전을 최종 선택했다. 이는 눈에 보이는 피드백 점수를 반복적으로 최적화하는 것이 과적합을 조장할 수 있음을 시사한다.

한계점

저자들이 스스로 밝힌 한계는 다음과 같다. 인간 기준선(human baseline)은 서로 다른 시스템에서 가져온 것으로 균일하지 않고 반드시 최적이라는 보장이 없다. Unified-Eval도 실행자-하네스 간 복잡한 상호작용을 완전히 제거하지는 못한다. Evolution 실험은 창작자-실행자 조합당 하나의 궤적만 있어 불확실성 추정이나 모집단 수준 비교를 지원하지 못하며, held-out 일반화 평가도 SWE-Pro 한 벤치마크에만 국한된다. 개발 환경(D) 자체는 두 단계 모두에서 고정되어 있어, 진화된 하네스가 스스로 다음 진화의 개발 환경 역할을 할 수 있는지는 다루지 않았다. 또한 이 연구는 모델 외부적 학습(하네스 개선)을 측정할 뿐, 이러한 휴리스틱 학습이 파라미터 학습을 대체할 수 있다고 주장하지 않는다.

시사점

이 연구는 에이전트 평가의 초점을 "고정된 시스템 안에서 과제를 풀 수 있는가"에서 "미래 과제를 풀어낼 시스템 자체를 만들고 유지보수할 수 있는가"로 옮긴다는 점에서 의의가 있다. 모델 가중치가 지능이 축적되는 한 장소라면, 하네스는 명시적이고 검사 가능하며 테스트 가능하고 재사용 가능한, 실패와 피드백과 실제 엔지니어링 압력을 통해 지속적으로 개선될 수 있는 또 다른 지능의 저장소라는 저자들의 주장은, 향후 에이전트 시스템 설계에서 모델과 하네스를 분리해 각각의 발전 경로를 추적해야 함을 시사한다. 특히 하네스 진화가 겉보기 성능 향상에도 불구하고 불안정하고 실행 모델 간 전이가 어렵다는 발견은, 자기 개선형 에이전트를 실제로 신뢰하기 위해서는 가시적 피드백 점수 최적화를 넘어선 별도의 견고한 일반화 검증 절차가 필요함을 시사한다.
