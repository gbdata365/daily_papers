Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents

패크 라이트, 캐리온: 장기 과업 에이전트를 위한 객체지향 컨텍스트 구축

장기간 실행되는(long-horizon) LLM 에이전트가 과거 상호작용 기록을 반복해서 다시 읽는 대신, 이미 확보한 "재사용 가능한 작업 결과물(task object)"을 중심으로 컨텍스트를 객체지향적으로 재구성하는 런타임 CarryOn을 제안하여, 토큰 사용량을 크게 줄이면서도 작업 성능을 끌어올린다.

한 줄 요약

장기간 실행되는(long-horizon) LLM 에이전트가 과거 상호작용 기록을 반복해서 다시 읽는 대신, 이미 확보한 "재사용 가능한 작업 결과물(task object)"을 중심으로 컨텍스트를 객체지향적으로 재구성하는 런타임 CarryOn을 제안하여, 토큰 사용량을 크게 줄이면서도 작업 성능을 끌어올린다.

배경 및 문제의식

장기 과업을 수행하는 에이전트는 두 종류의 정보를 함께 쌓아간다. 하나는 지속되는 "작업 상태"(예: 이미 수정된 문서, 이미 채워진 표)이고, 다른 하나는 그 상태가 "어떻게" 만들어졌는지를 설명하는 상호작용 기록(히스토리)이다. 문제는 작업이 길어질수록 에이전트가 이미 완료된 결과를 설명하는 중복된 히스토리를 계속해서 다시 처리하게 된다는 점이다. 기존 연구들은 이 히스토리를 요약·검색·가지치기하거나 구조화된 진행 상태로 변환해 컨텍스트 증가를 억제해왔지만, 결국 재사용 가능한 작업 결과물 대신 "재구성된 진행 상황 설명"에 의존하기 때문에 실제 에이전트가 직접 들여다보고 수정하는 상태와 어긋날 위험이 있다.

핵심 기여

논문은 히스토리 압축 중심의 기존 접근 대신, 재사용 가능한 작업 객체(task object)를 장기 컨텍스트의 기본 단위로 삼는 "객체지향적 관점"을 제시한다. 이를 구현한 CarryOn은 에이전트의 컨텍스트를 세 가지 상호보완적 요소로 구성한다. - Continuation Carrier(연속성 캐리어): 재사용 가능한 콘텐츠나 외부 객체에 대한 참조를, 그것을 다시 사용하기 위한 조건과 함께 묶어 기록한다. - Execution Context(실행 컨텍스트): 캐리어에 담기지 않은 현재 목표, 제약 조건, 미해결 이슈 등 계속 작업을 이어가는 데 필요한 보조 정보를 유지한다. - Live Tail(라이브 테일): 가장 최근 fold(병합) 이후 누적된 원본 상호작용을 그대로 보존한다.

방법론

CarryOn은 Tracker, Grounder, Compiler라는 세 구성요소가 협력하여 네 단계로 컨텍스트를 갱신한다. 1) Tracker가 재사용 가능해질 후보 진행 상황을 추적하고, 컴파일(정리)이 필요한 시점에 요청한다. 2) 컴파일 전 단계에서 후보를 뒷받침할 근거(소스, 참조 객체, 상태 등)를 수집하며, Grounder가 관련 환경 조건을 읽기 전용으로 점검한다. 3) Compiler가 선택된 후보와 기존 캐리어 레코드, 실행 컨텍스트, 라이브 테일의 텍스트 투영을 입력받아 캐리어 수정안과 새로운 실행 컨텍스트를 동시에 제안한다. 4) 검증 단계에서 제안된 수정이 현재 버전 및 근거와 일치하는지 확인한 뒤, 통과하면 "fold"를 통해 해당 상호작용 기록을 캐리어·실행 컨텍스트로 대체하고 커밋한다. 캐리어는 외부 객체(파일 등), 정보 산출물(종합된 발견), 상황적 상태(특정 환경·세션에 묶인 진행 상황) 세 가지 유형으로 나뉘며, 매 fold마다 영향을 받은 레코드만 개정되고 나머지는 그대로 이월되어 전체 표현을 매번 처음부터 재구성하지 않는다.

실험 설정 및 결과

Claude Opus 4.7을 호스트 에이전트이자 CarryOn의 Tracker·Compiler 모델로 사용하여, 컴퓨터 사용 장기 과업 벤치마크인 OSWorld 2.0 전체와 장기 웹 검색 벤치마크인 BrowseComp-Plus의 100문항 무작위 부분집합에서 평가했다. OSWorld 2.0에서 CarryOn은 partial 점수를 43.9%에서 49.7%로(+5.8%p), binary 점수를 15.7%에서 19.4%로 끌어올리면서 전체 토큰 사용량을 51.9%, 작업당 비용을 35.9% 절감했다. BrowseComp-Plus에서는 정확도가 49%에서 56%로(+7%p) 상승하면서 토큰 사용량 22.9%, 비용 7.1%가 줄었다. 실행 턴이 늘어날수록 베이스라인의 입력 컨텍스트는 200K 토큰을 넘어 계속 증가하는 반면, CarryOn은 약 65K 토큰 수준에서 안정화되었으며, 비용 절감 효과도 턴이 길어질수록(turn 500 기준 약 34.1%) 더 커졌다. 또한 단순 슬라이딩 윈도우나 일반적인 요약 압축과 비교했을 때 CarryOn의 객체지향 원칙은 동일한 원칙을 텍스트 요약에 적용한 방식(CarryOn-Guided Summary)보다도 더 높은 partial 점수(55.93% vs 50.93%)를 보였고, 캐리어 또는 실행 컨텍스트 중 하나만 제거하는 ablation 실험에서는 둘 다 성능 저하(특히 캐리어 제거 시 에이전트 호출 수와 비용 증가)로 이어져 두 요소가 상호보완적임을 확인했다.

한계점

논문에 명시된 한계는 다음과 같다. 현재 구현에서는 fold가 라이브 테일 전체를 한 번에 커버하는 방식으로만 이루어지며, 검증 단계의 점검은 업데이트의 일관성과 근거 적합성만 보장할 뿐 과업 자체의 정답 여부(correctness)를 검증하지는 않는다고 명시되어 있다. 그 외 세부적인 실패 사례 분석이나 다른 모델·도메인으로의 일반화 가능성에 대한 구체적 논의는 논문에 명시되지 않음.

시사점

이 연구는 장기 호라이즌 에이전트의 컨텍스트 관리를 "히스토리를 얼마나 잘 압축하느냐"의 문제에서 "재사용 가능한 작업 결과를 어떻게 1급 객체로 다룰 것인가"의 문제로 전환시킨다. 문서 편집, 웹 리서치처럼 명확한 작업 산출물이 존재하는 에이전틱 워크플로우에서 메모리·컨텍스트 설계 시 단순 요약·검색보다 객체(작업 결과) 단위의 구조화가 비용과 성능 양면에서 더 유리할 수 있음을 시사하며, 향후 에이전트 프레임워크나 메모리 시스템 설계에 참고할 수 있는 구체적 아키텍처 패턴을 제공한다.
