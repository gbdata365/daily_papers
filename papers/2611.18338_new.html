MEM-SQL: Memory-Empowered Text-to-SQL

한 줄 요약

동일 데이터베이스에 반복적으로 질의가 들어올 때 과거의 검증된 SQL 질의를 재사용해 정확도를 높이고 생성 비용을 낮추는 "메모리 기반" Text-to-SQL 기법 MEM-SQL과, 이를 평가하기 위한 히스토리 인지 벤치마크 HARE를 함께 제안.

배경 및 문제의식

Spider, BIRD 같은 기존 Text-to-SQL 벤치마크는 질문들을 독립적으로 평가해, 동일 데이터베이스에 대해 사용자가 반복적으로 질의하는 실제 상황—이전 질의가 새 질문에 필요한 조인이나 계산 일부를 이미 제공하는 경우—을 간과한다. 과거의 검증된 질의에 접근할 수 있다면 스키마로부터 동일한 로직을 매번 재구성하는 비용이 큰 작업을 피할 수 있지만, 질의 하나가 실행은 되더라도 그 로직의 일부가 더 이상 새 요청과 맞지 않을 수 있어, 히스토리의 가치를 측정하려면 "요청 간에 무엇이 이어지는지"를 식별하고 그것이 정확도와 생성 비용에 미치는 영향을 다양한 편집 유형에 걸쳐 측정할 수 있는 벤치마크가 필요했다.

핵심 기여

  • Spider, BIRD, Spider 2.0, BEAVER에서 추출한 823개의 검증된 질의를 바탕으로 1,600개의 요청을 만들고, 6개의 단일(primitive) 범주와 6개의 복합(composite) 범주로 "어떤 히스토리 구성요소를 보존하고 어떤 편집이 필요한지"를 명시한 벤치마크 HARE(History-AwaRe Text-to-SQL BEnchmark) 제안.
  • 전체 질의 템플릿, 재사용 가능한 SQL 블록(SELECT 블록), 도메인 개념-스키마 요소 매핑이라는 3단계 계층형 메모리를 저장하는 MEM-SQL 설계.
  • 각 계층은 자신에게 할당된 모든 요구사항이 임계값 이상으로 매칭될 때만 사용되도록 하는 커버리지 게이트(coverage gate) 도입.
  • 어떤 계층도 조건을 만족하지 못하거나 생성기가 검색된 증거를 불충분하다고 판단할 때만 스키마를 조회하는 "온디맨드 스키마 링킹(On-demand Schema Linking, OSL)" 기법 제안.

방법론

MEM-SQL은 과거의 검증된 SQL로부터 세 가지 세분화 수준(전체 질의 템플릿, 재사용 가능한 쿼리 블록, 스키마 개념 매핑)의 메모리를 구축한다. 새 요청이 들어오면 검색 가능한 설명을 통해 새로운 문구를 저장된 SQL 구조·컬럼 매핑에 연결하고, 각 요구사항별로 커버리지를 개별적으로 확인한다. 한 계층은 자신에게 할당된 모든 요구사항이 요구 임계값을 넘겨 매칭되어야만 기여할 수 있어, 강한 매칭 하나가 커버되지 않은 다른 요구사항을 가리는 것을 방지한다. OSL은 모델의 불확실성에만 의존하지 않고, 어떤 메모리 계층도 조건을 만족시키지 못하거나 생성기가 검색된 증거로 충분하지 않다고 판단할 때만 스키마를 추가로 조회한다.

실험 설정 및 결과

6개의 언어모델에 대해 HARE로 평가한 결과, 평균 실행 정확도가 히스토리 없이 직접 생성(Direct Generation)하는 방식의 37.1%에서 MEM-SQL의 50.0%로 상승했으며, 평균적으로 입력 토큰은 76.6% 적게, 지연시간은 68.8% 낮게 소요되었다. 어블레이션 결과 메모리 계층별로 역할이 달랐다: 템플릿은 정확도 향상에 가장 크게 기여했고, 쿼리 블록은 특히 여러 구성요소를 조합(composition)해야 하는 경우에 중요했다. 다만 여러 검증된 질의를 재사용해야 하는 요청은 여전히 병목으로 남아, 정확도가 56.7%에서 29.7%로 크게 떨어졌으며, 재사용된 구성요소를 새로운 질의 구조에 배치하거나 공유 조인과 결합해야 할 때 가장 급격히 저하되었다. OSL을 다른 3개의 메모리 설계에 적용했을 때도 생성 비용은 일관되게 줄었지만, 정확도 개선 효과는 메모리 설계가 얼마나 완전한 증거를 검색해낼 수 있는지에 따라 달라졌다.

한계점

저자들이 직접 명시한 한계로, HARE는 기업 데이터베이스에서 흔한 "스키마 드리프트"(예: 회계연도 시작 월 같은 개념의 정의가 바뀌는 경우)를 모델링하지 않는다. 또한 MEM-SQL은 정적(static) 메모리로 평가되었기 때문에, 메모리를 추가·갱신·폐기하는 동적 환경에서의 성능 변화는 아직 밝혀지지 않았다. 마지막으로 실행 정확도 지표는 반올림 등 형식만 다른 답을 틀린 것으로 처리하며, 올바른 결과를 반환하지만 잘못된 이유로 그런 SQL은 탐지하지 못한다는 한계가 있어, 향후 평가는 "의도(intent)"까지 함께 평가해야 한다고 제안한다.

시사점

검증된 질의 히스토리는 생성을 더 정확하고 더 저렴하게 만들 수 있지만, 그 가치는 "어떤 증거를 유지하는지"와 "시스템이 언제 스키마를 조회하는지"에 달려 있다. 저자들은 메모리 세분화 수준을 분리해 설계하는 것(전체 질의 재사용 대 부분 구성요소 재사용)과, 모델 불확실성이 아닌 커버리지 기반으로 스키마 조회 시점을 결정하는 것이 효율성과 정확도를 동시에 개선하는 핵심이라고 제안한다.
