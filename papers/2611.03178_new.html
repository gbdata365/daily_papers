CoworkOS: Scaling Agent Coworkers for Real-world Automation

코워크오에스: 실세계 자동화를 위한 에이전트 코워커 확장

작업 전략 결정은 모델에, 상태·피드백 관리는 런타임에 맡기는 3계층 구조(Main Agent·Coordinator Runtime·Subagent)로 복잡한 생산성 작업과 장기간 모니터링을 동시에 지원하는 범용 에이전트 하네스 CoworkOS를 제안하고, 이를 이용해 모델 후처리까지 자동화한 사례를 보임.

한 줄 요약

작업 전략 결정은 모델에, 상태·피드백 관리는 런타임에 맡기는 3계층 구조(Main Agent·Coordinator Runtime·Subagent)로 복잡한 생산성 작업과 장기간 모니터링을 동시에 지원하는 범용 에이전트 하네스 CoworkOS를 제안하고, 이를 이용해 모델 후처리까지 자동화한 사례를 보임.

배경 및 문제의식

사람과 AI가 함께 소프트웨어·문서·디자인 등 결과물을 만들어가는 '코워크(cowork)' 작업은 (1) 복잡한 추론·도구 사용·검증이 필요한 고난도 생산성 작업과 (2) 며칠에서 몇 주에 걸쳐 진행 상황을 모니터링하고 판단해야 하는 장기 작업이라는 서로 다른 두 요구를 동시에 만족해야 한다. 기존 코딩/업무 에이전트(Claude Code, Codex, OpenHands, DeepSeek Harness 등)는 주로 전자에 특화되어 있어, 두 요구를 하나의 범용 하네스로 함께 다룰 수 있는지가 미해결 과제로 남아 있었다.

핵심 기여

  • 작업 실행 전략은 모델이 스스로 결정하고, 효율적인 장기 코워크 메커니즘(상태 관리, 위임, 피드백 수용)은 런타임이 담당하도록 책임을 분리한 3계층 아키텍처(Main Agent, Coordinator Runtime, Subagent)를 가진 코워크 하네스 CoworkOS를 제안.
  • 문서·프레젠테이션·CAD·Blender 등 다양한 전문 애플리케이션을 네이티브 또는 MCP로 연동하고, 사람과 에이전트가 동일한 진화하는 산출물(문서·모델·장면)을 함께 열람·수정할 수 있는 공유 애플리케이션 생태계를 구축.
  • 계층적 작업공간(workspace)과 영속적 의미 기억(semantic memory)을 도입해, 작업 파일·핵심 결정·장기 실행 중인 Job의 로그가 세션이 끊겨도 재사용·재개 가능하도록 지속성을 확보.
  • 12개 벤치마크(도구 사용·생산성·검색·ML 코딩 4개 영역)와 6개 범주의 실제 애플리케이션 사례(웹사이트·게임·오피스 문서·인터랙티브 시각화·CAD·Blender)에서 OpenHands, Codex, DeepSeek Harness 같은 최신 코워크 하네스와 경쟁력 있는 성능을 보임.
  • CoworkOS가 GLM-5.3을 컨트롤러로 삼아 Qwen3.6-35B-A3B 모델의 후처리(post-training)를 스스로 분석·개선·검증·재학습하는 재귀적 자기개선(RSI) 사례 연구를 수행해, 5회 반복만에 8개 벤치마크 평균 점수를 33.19에서 42.95로(+9.76점) 끌어올림.

방법론

에이전트 작업을 목표 g, 환경 E, 행동 공간 A, 수용 기준 V, 자원 예산 B로 정의하고, Main Agent는 사용자의 전체 맥락을 유지하며 계획·실행·검토·수용을 담당하고, Coordinator Runtime은 호출 레지스트리·스케줄러·수신함·Job 모니터링을 통해 Main과 Subagent 간의 위임을 동기 또는 비동기로 전달하며, Subagent는 격리된 맥락에서 할당된 작업을 수행한 뒤 보고서와 근거를 반환하는 구조로 동작한다. 공유 애플리케이션 레이어에서는 자원을 (식별자, 종류, 내용, 리비전) 튜플로 표현해, 사람과 에이전트의 편집이 기준 리비전이 다르면 충돌로 처리되고 그렇지 않으면 리비전이 갱신되는 방식으로 동시 편집을 관리한다(커밋 규칙 수식 (7)). 상태 관리 측면에서는 작업 상태를 (작업 객체 W, 진행·결정·근거 P, 실행·대기조건·보류피드백 R)으로 표현해, 긴 연산이 백그라운드 Job으로 지속되고, 체크포인트를 통해 중단 후에도 정확히 재개할 수 있도록 하며, Main의 의미 기억 문서와 압축(compaction) 메커니즘으로 컨텍스트 용량을 넘지 않게 작업 이력을 관리한다. RSI 사례 연구에서는 GLM-5.3이 컨트롤러 겸 데이터 교사 역할로 모델 평가 → 역량 격차 진단 및 데이터 파이프라인 수정 → 데이터 생성·검증·필터링 → SFT → 재평가의 폐쇄 루프를 반복한다.

실험 설정 및 결과

CoworkOS는 GLM-5.3(고강도 사고 모드, 256K 토큰 컨텍스트)을 기반 모델로 사용해 SkillsBench·Tau3-Bench Banking·AutomationBench(도구 사용), JobBench·Harvey Legal Agent Bench·GDPVal·OfficeQA Pro·WorkspaceBench-Lite(생산성), WideSearch·BrowseComp(검색), MLE-Bench-Lite·MLS-Bench(ML 코딩) 등 12개 벤치마크에서 OpenHands, Codex, DeepSeek Harness(DSH)와 비교되었다. CoworkOS는 생산성(평균 57.54점, DSH 56.13점)과 ML 코딩(평균 56.26점) 영역에서 1위를 기록했고, 도구 사용(55.22점, DSH 55.31점)과 검색(82.14점, OpenHands 82.22점)에서는 근소한 차이로 2위를 기록해 네 영역 모두에서 상위권을 유지했다. 24개 실제 애플리케이션 사례(웹사이트·게임·오피스 문서·인터랙티브 시각화·CAD·Blender 장면)에 대한 정성 비교에서는, CoworkOS가 산출물의 정보를 더 명확하게 정리하고 더 풍부한 세부 구조(예: 조립 상세, 재질 구분)를 제공하는 경향이 관찰되었다. RSI 기반 자동 후처리 사례 연구에서는 Qwen3.6-35B-A3B의 8개 벤치마크 평균 점수가 초기 시드 SFT 기준 33.19에서 5회 반복 후 42.95로 상승했으며, Automation(+33.15점)과 SkillsBench(+14.91점)에서 가장 큰 향상을, Harvey LAB·Tau3 Banking·OfficeQA Pro에서는 더 꾸준한 향상을 보였다.

한계점

논문에 '한계점'이라는 별도 절은 없으나 본문에서 다음과 같은 제약이 드러난다. RSI 자동 후처리 실험에서 모든 과제가 매 라운드마다 균일하게 개선되지는 않았으며(BFCL v4는 R1~R4 동안 초기 기준보다 낮게 유지되다가 R5에서야 개선), 하나의 학습 데이터셋으로 여러 과제 성능을 동시에 끌어올려야 하는 데 따른 과제 간 트레이드오프가 라운드마다 다르게 나타났다(예: R1에서 시드 데이터 재학습 비중이 지나치게 높아 R2에서 평균 점수가 36.94에서 35.90으로 일시 하락). 또한 애플리케이션 생태계 연동에서 MCP로 연결된 외부 소프트웨어는 플랫폼이 보장할 수 없는 자체 저장·동시성 규칙을 그대로 따르기 때문에, 네이티브 연동과 달리 완전한 리비전 관리 보장을 제공하지 못한다.

시사점

작업 전략 결정(모델의 역할)과 장기 상태·피드백 관리(런타임의 역할)를 명확히 분리하는 설계가, 단발성 작업 자동화를 넘어 사람과 에이전트가 동일한 산출물을 두고 오랜 기간 함께 작업하는 '코워크' 시나리오를 지원하는 데 효과적임을 보여준다. 특히 모델 후처리 과정 자체를 에이전트가 모니터링·판단하며 반복 개선하는 RSI 사례는, 향후 에이전트 하네스가 단순 작업 실행을 넘어 모델 개선 루프 자체를 관리하는 방향으로 확장될 수 있음을 시사한다.
