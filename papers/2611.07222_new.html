SPILLWAY: Separating Target Admission from Sanitization to Defend Tool-Using Agents against Prompt Injection

스필웨이: 목적지 승인과 새니타이제이션의 분리로 도구 사용 에이전트를 프롬프트 인젝션으로부터 방어하기

도구를 사용하는 LLM 에이전트를 간접 프롬프트 인젝션으로부터 지키기 위해, "어디로 행동이 나가도 되는가(egress)"를 결정하는 모델-없는 규칙 기반 체크와 "에이전트가 무엇을 읽는가(ingress)"를 정리하는 결정적 새니타이저를 분리해 결합한 방어 기법 SPILLWAY를 제안한다.

한 줄 요약

도구를 사용하는 LLM 에이전트를 간접 프롬프트 인젝션으로부터 지키기 위해, "어디로 행동이 나가도 되는가(egress)"를 결정하는 모델-없는 규칙 기반 체크와 "에이전트가 무엇을 읽는가(ingress)"를 정리하는 결정적 새니타이저를 분리해 결합한 방어 기법 SPILLWAY를 제안한다.

배경 및 문제의식

이메일, 파일, 결제 등 외부 도구를 다루는 에이전트는 웹페이지나 공유 문서, 이메일 본문처럼 공격자가 작성할 수 있는 텍스트를 읽다가 숨겨진 지시를 실행해버리는 간접 프롬프트 인젝션에 취약하다. 기존 런타임 방어들은 대부분 또 다른 모델 호출을 추가해 공격자가 작성한 텍스트를 다시 읽게 하거나(MELON, Progent, DRIFT), 작업을 먼저 계획·라우팅하는 플래너 모델에 의존한다(ROPE, CaMeL). 저자들은 "행동의 목적지(target)가 어디서 왔는가"는 도구가 반환하는 타입이 있는 필드(이메일 발신자, 결제 수신 계정 등)만 보면 모델 없이도 판별할 수 있다는 점에 착안한다.

핵심 기여

  1. 타입이 있는 도구 반환값만으로 행동 목적지를 허용/차단하는 결정적 "egress 바닥(floor)" 제시 — 별도의 per-task 라우팅 모델 없이 12개 백본×스위트 조합 모두에서 공격 성공률 0 달성.
  2. 새니타이저(ingress)가 제거한 영역을 판정 모델(judge)이 다시 열람하지 못하도록 결합한 구조 — 새니타이저 없이 judge만 두면 공격자 계정으로의 송금을 허용해버리는 취약점을 실험으로 확인.
  3. 라우팅 기반 방어(ROPE)와의 정면 비교 — SPILLWAY는 7개 위임 라우팅 스위트 전부와 ChatInject 두 스위트에서 공격 성공률 0이면서 더 높은 유용성을 유지, 에이전트 자신이 라우터 역할을 하면 ROPE는 누출이 발생.

방법론

SPILLWAY는 두 개의 경계를 지킨다. (A) Egress gate: 제안된 도구 호출의 목적지 값이 신뢰된 타입 ID 인덱스(읽기 전용 도구가 반환한 이메일/URL/계정 등)에 있고 사용자 평문에 반복되지 않았으면 허용하고, 그 외에는 위임 규칙이나 2단계(two-view) judge를 거쳐야만 통과한다(Algorithm 1). (B) Ingress 새니타이저: 모델이 읽기 전 위조된 채팅 템플릿 턴, 지시문 형태의 블록, 공격자가 꾸민 계좌 변경 주장을 결정적 규칙으로 찾아 placeholder로 치환하고 제거된 영역을 증거로 보관한다. 거부된 목적지가 이 제거 영역 안에 있으면 judge에게 다시 묻지 않는 "span veto"로 judge의 재열람을 차단한다. judge는 온도 0의 로컬 모델이며, 판정이 애매하면 무조건 거부(fail-closed)한다.

실험 설정 및 결과

AgentDojo(4개 스위트×3개 백본: gpt-4o-mini, qwen3-coder:30b, qwen3:8b)의 표준 공격과, ChatInject·AutoDojo 최적화 인젝션·공개된 강화학습 공격기 PISmith를 포함한 스트레스 테스트, 그리고 AgentDyn 기반 위임 라우팅 세팅에서 평가했다. SPILLWAY는 표준 공격의 12개 셀 전부에서 공격 성공률(in-scope ASR) 0을 기록한 유일한 방어였으며, 공격을 받는 상황에서의 유용성(UAU)도 가장 높았다(0.489, 무방비 에이전트는 0.489 중 0.539). 위조 채팅 템플릿 공격(ChatInject)에서도 원시(raw) 공격 성공 0, 공개 RL 공격기 PISmith 아래서도 평균 ASR 0.005로 비교 대상 중 최저 수준을 보였다. 모델 호출 비용 측면에서도 벤치마크당 judge 호출이 0.43회 이하로 MELON·DRIFT·Progent 대비 훨씬 적은 추가 호출만 발생했다.

한계점

SPILLWAY의 보장은 "신원(identity) 목적지"에 국한된다. 즉, 인젝션이 사용자의 기존 연락처나 실제 결제 대상처럼 이미 신뢰된 신원으로 행동을 유도하는 경우는 이 가드의 범위 밖이며, 도구 출력에 그대로 나타나지 않는(verbatim하지 않은) 목적지도 핵심 보장(P1) 밖에 있다. 목적지 역할은 벤치마크마다 한 번씩 수작업으로 정의한 어휘집(lexicon)에서 오므로, 새로운 도구 집합에는 이 어휘집을 새로 작성해야 한다. 또한 floor는 분류기가 아니라 집합 조회(set lookup)이므로 인젝션 문구 자체를 바꾸는 것은 막지 못하며, 적응형 공격자가 노릴 수 있는 지점(judge, 위임 규칙, 어휘집)은 저자들도 한계로 명시한다.

시사점

개인 비서형 AI 에이전트가 사용자의 메일·캘린더·결제를 실제로 조작하게 되면서, 프롬프트 인젝션 방어가 모델 호출을 늘리지 않으면서도 구조적으로 안전성을 보장할 수 있다는 점을 보여준다. 도구가 이미 제공하는 타입 정보를 활용해 별도의 라우팅 모델 없이 결정적으로 공격을 차단할 수 있다는 아이디어는, 향후 MCP 기반 에이전트 생태계 전반에 가볍게 적용 가능한 보안 계층으로 확장될 잠재력을 시사한다.
