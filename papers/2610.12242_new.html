TokenRouter: Efficient Serving System for Token-Level LLM Routing

토큰라우터: 토큰 단위 LLM 라우팅을 위한 효율적인 서빙 시스템

토큰 단위로 여러 LLM을 오가며 생성하는 "토큰 레벨 라우팅"을 기존 서빙 시스템(vLLM, SGLang 등)보다 최대 64배 빠르게 처리할 수 있는 전용 서빙 시스템, TokenRouter를 제안한다.

한 줄 요약

토큰 단위로 여러 LLM을 오가며 생성하는 "토큰 레벨 라우팅"을 기존 서빙 시스템(vLLM, SGLang 등)보다 최대 64배 빠르게 처리할 수 있는 전용 서빙 시스템, TokenRouter를 제안한다.

배경 및 문제의식

LLM 라우팅은 비용과 품질의 Pareto frontier를 넓히기 위해 여러 모델에 추론 작업을 분산시키는 기법이다. ChatGPT, Cursor 같은 상용 시스템이나 RouteLLM 같은 연구는 세션 또는 쿼리 단위로 요청 전체를 하나의 모델에 라우팅하는 방식(coarse-grained routing)을 사용한다. 그러나 최근 연구들(R2R, CITER, Co-LLM, R-Stitch, ME 등)은 토큰 단위로 라우팅하면 효율과 품질 모두에서 더 큰 이득을 얻을 수 있음을 보였다. 예를 들어 R2R은 토큰의 5%만 32B 모델로 보내도 쿼리의 40%를 32B로 보내는 것과 동등한 품질을 달성한다.

문제는 기존 서빙 시스템(SGLang, vLLM 등)이 "단일 LLM이 모든 스텝에서 동기적으로 디코딩한다"는 가정 위에 설계되어 있다는 점이다. 토큰 레벨 라우팅은 매 디코딩 스텝마다 대상 모델이 바뀔 수 있으므로 다음 세 가지 문제가 발생한다. 1. 스텝 비동기화(step desynchronization): 모델별 스텝 지연시간이 크게 다른데, 하나의 배치로 동기화하면 가장 느린 모델을 기다리느라 빠른 모델이 유휴 상태가 된다. 2. 배치 승인 지연(batch admission delay): 라우팅된 요청이 목적 모델에 도착해도 그 모델이 이미 다른 배치를 처리 중이면 다음 배치까지 대기해야 하고, 이로 인해 배치가 파편화된다. 3. 구현 복잡성: 기존 서빙 시스템은 스텝 단위 라우팅 결정을 위한 프로그래밍 인터페이스를 제공하지 않아, 연속 배칭(continuous batching)이나 prefix caching 등 기존 기능과 라우팅 로직을 조율하려면 대규모 코드 수정이 필요하다.

핵심 기여

논문은 "request-centric programming, model-centric execution"이라는 설계 원칙 아래 세 가지 핵심 기여를 제시한다. - 요청 중심(request-centric) 프로그래밍 인터페이스: route-send-receive라는 3개 함수만으로 개발자가 단일 요청이 협력 LLM들 사이를 어떻게 이동하는지 기술하면, 다양한 토큰 레벨 라우팅 알고리즘을 표현할 수 있다. - 비동기 실행을 통한 서빙 최적화: 모델별로 독립적인 subserver를 두고, 스텝 비동기화 문제를 해결하는 분리된 "tri-loop(3중 루프)" 실행 구조와 모델 간 전환을 단순화하는 handoff-resume(인수인계-재개) 메커니즘을 제안한다. - 지연 배칭(delayed batching)을 통한 스케줄링 최적화: 평균 배치 승인 지연을 줄이는 지연 배칭 스케줄러를 제안하고, 처리량 기반 수학적 모델에서 유도한 최적 하이퍼파라미터를 사용한다.

실험 결과 TokenRouter는 다양한 라우팅 알고리즘·워크로드·모델 조합에서 기존 구현체 대비 디코딩 처리량을 2.01~64.15배 향상시켰다.

방법론

프로그래밍 인터페이스(route-send-receive): 토큰 레벨 라우팅 알고리즘들의 공통 수명주기를 receive → decode → route → send → peer receive → peer decode → ...로 정리하고, 개발자는 다음 세 함수만 구현한다. - route(result): 각 디코딩 스텝 이후 forward-pass 결과(히든 스테이트, 다음 토큰 로짓, 샘플링된 토큰 등)를 바탕으로 각 요청의 목적지(로컬 계속 혹은 다른 모델)를 결정. - send(req): 라우팅이 결정되면 요청 ID, peer가 아직 보지 못한 토큰 suffix, 종료 여부, 위치 anchor(req.loc) 등을 담은 PeerReq 메시지를 생성. - receive(peer_req): 도착한 PeerReq를 로컬 요청 형식으로 변환(기본값은 전달된 토큰을 모두 수용). 알고리즘별로 필요한 경우만 override.

논문은 R-Stitch(엔트로피 기반 라우팅)를 예시로 이 인터페이스로 코드 몇 줄에 알고리즘을 표현할 수 있음을 보이고, CITER·R2R·R-Stitch·Co-LLM·ME 등 5개 알고리즘의 라우팅 조건을 표로 정리한다.

시스템 아키텍처(모델 중심 런타임): 각 LLM은 독립된 subserver로 호스팅되며, 자체 스케줄러·LLM 러너·KV-cache 풀, 그리고 사용자 정의 route/send/receive 함수를 가진다. 외부에는 단일 서버 인터페이스만 노출되어 기존 vLLM/SGLang과 동일한 클라이언트 프로토콜로 동작하는 drop-in replacement 역할을 한다.

비동기 실행(tri-loop + handoff-resume): 표준 서버의 client-server 루프(요청 수신·응답 스트리밍)와 decoding 루프(스케줄링·모델 실행) 외에, inter-model 루프(모델 간 peer request 송수신)를 추가로 분리한다. 라우팅된 요청이 로컬 배치를 떠나 있는 동안 나머지 로컬 요청들은 자신의 속도로 계속 진행한다. 또한 pending이라는 중간 상태를 도입해, 모델 간 전환 시 prefix matching이나 KV-cache 재할당을 다시 하지 않고 토큰만 append하는 식으로 handoff/resume 비용을 최소화한다.

지연 배칭(delayed batching): 요청이 도착하는 즉시 배치를 실행(eager-async)하면 배치가 자주 파편화된다. 대신 버퍼에 요청을 모아 크기가 임계값 B에 도달할 때 배치를 실행한다. 이때 B가 너무 작으면 승인 지연이 크고, B가 너무 크면 모델이 유휴 상태(starvation)에 빠지는 트레이드오프가 있다. 논문은 이 과정을 이산시간 마르코프 체인(Discrete-Time Markov Chain, DTMC)으로 모델링하여, 동시성 N, 라우팅 확률 P, 모델별 스텝당 지연시간 L을 입력으로 처리량을 B의 함수로 유도하고, 처리량을 최대화하는 최적 임계값 B*를 탐색한다.

구현은 SGLang을 기반으로 하며, CUDA 그래프 확장 등 라우팅에 특화된 추가 엔지니어링 최적화도 적용했다.

실험 설정 및 결과

실험 환경: 8×A100-80GB GPU 서버. CITER, R2R, R-Stitch, Co-LLM은 Qwen3-0.6B/Qwen3-32B 쌍에서 평가하고, ME는 Qwen3-0.6B/8B/32B 3개 모델로 평가. 작은 모델은 1 GPU, 큰 모델은 텐서 병렬 2 GPU에 배치(CUDA MPS로 공유). 비교 대상은 각 알고리즘의 공개 구현(Official Code)과, 저자들이 SGLang 기반으로 공정 비교를 위해 직접 구축한 Std. Serving(모델별 SGLang 서버 + 외부 디스패처) 두 가지.

워크로드: (1) Low-effort reasoning(AIME2024, 입출력 짧음, 출력 최대 2,048토큰), (2) High-effort reasoning(AIME2024, 출력 최대 8,192토큰), (3) Agentic(SWE-Smith 트레이스, 입력 약 8,192토큰, 출력 최대 1,024토큰).

주요 결과: - 15개 알고리즘-워크로드 조합 전체에서 TokenRouter가 더 강한 베이스라인 대비 처리량을 2.01~64.15배, 종단 지연(latency)을 Std. Serving 대비 2.03~63.64배 개선. - 원 논문의 기본 설정(original settings)에서도 공식 구현 대비 지연을 2.78~21.61배 줄이고 처리량을 2.73~21.97배 향상. - 출력 길이가 길어져도(2,048→8,192 토큰) TokenRouter의 처리량은 거의 유지되는 반면 Std. Serving은 58.1~85.2%의 처리량을 손실. - 처리량-속도(Throughput-Speed) 트레이드오프: 동시성을 1→16으로 늘릴 때 TokenRouter는 처리량 8.61배 증가, 사용자당 속도는 51.7% 유지(공식 R2R은 각각 5.14배, 31.3%). 동시성 16의 TokenRouter는 동시성 1의 공식 R2R보다 처리량 18.58배, 속도도 1.13배 높음. - Ablation(Fig.1a, 동시성 8): 기본 구현 132.78 token/s → CUDA 그래프 확장 230.79 → 비동기 실행 296.86 → 지연 배칭 372.48 token/s로, 공식 R2R(134.9 token/s) 대비 총 2.76배. - 다양한 SLM/LLM 모델 크기 조합(0.6B/8B, 0.6B/32B, 1.7B/8B, 4B/8B)에서도 R2R 공식 구현 대비 1.99~3.21배 처리량 향상. - 텐서 병렬 자원은 LLM 쪽에 배정하는 것이 SLM 쪽보다 처리량 향상에 훨씬 유리함(LLM TP 1→2 시 최대 40.6% 개선, 반면 SLM TP 추가는 1% 미만 개선). - 처리량-정확도 Pareto 분석(AMC23, Qwen3-0.6B/32B): TokenRouter가 토큰 레벨 라우팅(R2R)을 RouteLLM 기반 쿼리 레벨 라우팅(QR-MF/BERT/LLM/SW)보다 더 유리한 새로운 Pareto frontier로 이동시켜, 동일한 처리량에서도 더 높은 정확도를 달성.

한계점

논문이 명시한 한계는, 지연 배칭의 처리량 모델이 "두 연속 전송(send) 사이의 토큰 수가 기하분포(geometric distribution)를 따른다"는 가정에 기반한다는 점이다. 이는 대부분의 토큰 레벨 라우팅 알고리즘에는 성립하지만, 이 가정을 벗어나는 예외적인 경우(corner case)에 대한 처리는 향후 과제로 남겨두었다.

시사점

TokenRouter는 토큰 레벨 LLM 라우팅이라는, 알고리즘적으로는 유망하지만 실제 서빙 시스템에서는 거의 지원되지 않던 영역에 "요청 중심 프로그래밍, 모델 중심 실행"이라는 명확한 추상화를 제시함으로써, 라우팅 알고리즘 개발자가 저수준 배칭/스케줄링을 신경 쓰지 않고도 효율적인 서빙 성능을 얻을 수 있게 한다. 기존 단일 LLM 서빙 시스템과 호환되는 drop-in replacement 인터페이스를 제공하는 점, 그리고 수학적 처리량 모델에 기반해 스케줄링 하이퍼파라미터를 자동으로 도출하는 접근은 향후 다중 모델 협업 추론(speculative decoding, mixture-of-experts 서빙, 모델 앙상블 등) 시스템 설계에도 참고할 수 있는 일반적인 패턴을 제시한다. 처리량-정확도 Pareto frontier를 실제로 개선함으로써, 토큰 레벨 라우팅이 연구 단계를 넘어 production 수준의 비용-품질 최적화 기법으로 자리잡을 수 있는 실용적 기반을 마련했다는 점에서 의미가 크다.
