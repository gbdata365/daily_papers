OpenGCUA: Toward a Fully Open Stack for Generalist Computer Use

OpenGCUA: 범용 컴퓨터 사용을 위한 완전 개방형 스택을 향하여

GUI 클릭에만 의존하던 컴퓨터 사용 에이전트를 넘어, 모델이 관찰 방식·행동 방식·작업 상태 관리까지 스스로 결정하는 "범용 컴퓨터 사용 에이전트(Generalist Computer-Use Agent, GCUA)"를 정의하고, 이를 구현한 오픈소스 하네스(harness)와 프롬프트, 실행 트라젝토리를 공개한 보고서.

한 줄 요약

GUI 클릭에만 의존하던 컴퓨터 사용 에이전트를 넘어, 모델이 관찰 방식·행동 방식·작업 상태 관리까지 스스로 결정하는 "범용 컴퓨터 사용 에이전트(Generalist Computer-Use Agent, GCUA)"를 정의하고, 이를 구현한 오픈소스 하네스(harness)와 프롬프트, 실행 트라젝토리를 공개한 보고서.

배경 및 문제의식

컴퓨터 사용 에이전트(CUA) 연구는 주로 스크린샷을 보고 마우스·키보드로 조작하는 GUI 전용 에이전트에 집중되어 왔다. 그러나 GPT-6 Astra와 같은 최신 시스템들은 GUI 조작과 셸 명령, 접근성 트리(accessibility tree), API 호출을 결합해 코드로 작성하는 방식(code execution)을 채택하고 있다. 문제는 이런 프런티어 시스템들이 모델 가중치, 프롬프트 설계, 실제 기기용 하네스, 기기 제어 SDK, 실행 트라젝토리를 전부 비공개로 유지해, 커뮤니티가 설계를 재현하거나 비교·분석할 수 없다는 점이다.

핵심 기여

  • GCUA 정의: 각 단계에서 모델이 (1) 무엇을 관찰할지, (2) 어떻게 행동할지, (3) 작업을 어떻게 조직할지를 스스로 결정하는 에이전트를 GCUA로 정의하고, 기존 GUI 에이전트·CLI 에이전트·GUI+CLI 하이브리드 에이전트(자사의 이전 연구 Qwen-UI-Agent 포함)를 모두 이 틀 안의 특수 사례로 재구성함.
  • 코드 실행(Code Execution)의 효과 입증: 동일한 GUI/셸 접근 권한에서도, GUI 조작을 코드로 작성하고 프로그램적 연산과 결합하면 GUI+CLI 베이스라인 대비 평균 부분 점수(partial score) 6.1점 상승, 과업당 스텝 수 14.8% 감소.
  • 하네스-모델 결정 이전(Harness-to-Model Decision Transfer): 매 스텝 스크린샷을 찍는 등 하네스가 고정 규칙으로 처리하던 결정(언제 관찰할지, 작업 상태를 어떻게 추적할지)을 모델에게 넘기는 방식을 제안. 온디맨드 관찰만으로도 두 모델에서 캐시 적중률이 10.5~14.4%p 상승하면서도 과업 점수는 유지됨.
  • 실제 기기(real-device) 하네스와 기기 간(cross-device) SDK: 사용자가 실제로 사용 중인 macOS 환경에서 동작하는 5계층 구조의 실제 기기 하네스, 그리고 컴퓨터·브라우저·모바일을 하나의 인터페이스로 다루는 SDK의 예비 버전을 공개.
  • GPT-6 Astra, Claude Opus 5 등 8개 프런티어 모델의 실행 트라젝토리 전면 공개.

방법론

GCUA는 수식적으로 각 스텝에서 정책 πθ가 (관찰할 뷰 집합 qt, 실행할 프로그램 pt, 갱신된 작업 상태 mt+1)을 한꺼번에 결정하는 과정으로 formalize된다. 관찰 인터페이스는 스크린샷, 접근성 트리(AX Tree), CLI 출력, API 응답 네 가지이며, 행동은 이들 네 인터페이스에 대응하는 연산을 반복문·분기문·변수까지 포함하는 하나의 프로그램으로 작성한다. 기존 GUI 에이전트는 qt를 스크린샷으로, pt를 단일 GUI 연산으로, mt+1 갱신을 고정 하네스 규칙으로 각각 고정하는 특수 사례로 표현된다. 저자들이 이전에 공개한 Qwen-UI-Agent(배치된 GUI+CLI 행동)도 이 틀 안에서 더 제한된 특수 사례로 위치시킨다. 이를 바탕으로 OpenGCUA 하네스는 Python 런타임 안에서 PyAutoGUI와 bash() 호출을 결합한 프로그램 실행, 액션 의도(intent) 명시, 온디맨드 스크린샷 요청, 모델 주도의 작업 상태(todo) 추적을 구현한다. 실제 기기 하네스는 접근성 트리 우선 → 비전 → 포그라운드 입력 순으로 동작하며, 사용자와 화면을 공유하는 상황(백그라운드 창 조작, ask_user() 등)에 대응하는 5계층 구조를 갖는다.

실험 설정 및 결과

OSWorld-v2 오프라인 세트에서 GPT-6 Astra, Claude Opus 5, Gemini 3.8 Flash, GLM-5.3-Flash, Qwen3.8-Max, Qwen3.8-Flash, Kimi K3, DeepSeek-V4.1-Flash 등 8개 프런티어 모델을 평가했다. 배치된 GUI 전용 베이스라인과 비교해 OpenGCUA 하네스 적용 시 8개 모델 전부에서 성능이 향상되었으며, 평균 부분 점수가 19.6점 상승하고 과업당 스텝 수는 평균 53.0% 감소했다(예: GPT-6 Astra 67.1%→75.7%, DeepSeek-V4.1-Flash 28.0%→57.7%). 또한 가장 강한 모델과 가장 약한 모델 간 점수 격차도 절반 이상 줄었다. 실제 macOS 기기에서 수행한 4건의 케이스 스터디에서는, 동일한 하네스를 사용했음에도 Qwen3.8-Max가 GPT-6 Astra보다 19.4배 많은 추론 토큰(50.2K vs 2.6K)과 5.7배 많은 전체 출력 토큰을 사용했지만 완료한 과업 수는 더 적었다. 이는 단순 연산에도 과도한 추론 비용을 들이거나, 실제 기기 환경 적응력과 코드 실행 능력에서 모델 간 격차가 크다는 점을 보여준다.

한계점

이번 공개는 프로젝트의 1차 릴리스로, 학습된 GCUA 모델 자체는 아직 포함되지 않았다(기존 프런티어 모델에 하네스만 적용한 결과). 실제 기기용 하네스와 기기 간 SDK도 예비(preliminary) 버전이며, 실제 기기 환경을 반영한 전용 벤치마크는 아직 공개되지 않았다. 그 외 세부 한계는 논문에 명시되지 않음.

시사점

컴퓨터 사용 에이전트의 설계 축을 "GUI냐 CLI냐"의 이분법에서 "모델이 관찰·행동·작업 관리 방식을 스스로 선택하게 할 것인가"라는 보다 일반적인 질문으로 옮겼다는 점에서 의미가 있다. 특히 하네스의 고정 규칙을 모델에게 점진적으로 이전하는 접근은, 모델 성능이 향상될수록 에이전트 프레임워크가 더 적은 외부 규칙으로도 효율을 얻을 수 있음을 보여주며, 향후 폐쇄형 프런티어 시스템(GPT-6 Astra 등)의 설계를 공개적으로 재현·비교하는 연구 기반을 제공한다.
