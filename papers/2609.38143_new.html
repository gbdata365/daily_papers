Learning Meta-Skills for Agent Harness Design in Test-Time AI4AI

테스트타임 AI4AI를 위한 에이전트 하네스 설계 메타스킬 학습

가중치가 고정된 두 모델을 "Builder(설계자)"와 "Target(실행자)"로 나누고, Builder가 Target의 실행 피드백으로부터 "언제·무엇을·어떻게 지원할지"를 담은 재사용 가능한 원칙인 메타스킬(meta-skill)을 학습하여 테스트 시점마다 과제별 실행 환경(하네스)을 새로 설계하게 하면, 같은 지식을 Target에게 직접 가르치는 것보다 훨씬 큰 성능 향상을 얻을 수 있다.

한 줄 요약

가중치가 고정된 두 모델을 "Builder(설계자)"와 "Target(실행자)"로 나누고, Builder가 Target의 실행 피드백으로부터 "언제·무엇을·어떻게 지원할지"를 담은 재사용 가능한 원칙인 메타스킬(meta-skill)을 학습하여 테스트 시점마다 과제별 실행 환경(하네스)을 새로 설계하게 하면, 같은 지식을 Target에게 직접 가르치는 것보다 훨씬 큰 성능 향상을 얻을 수 있다.

배경 및 문제의식

에이전트의 성능은 모델 자체의 추론 능력뿐 아니라 그 모델이 활동하는 실행 환경(하네스)에도 크게 좌우된다. 최근 "AI를 위한 AI(AI4AI)" 연구들은 에이전트 프로그램·워크플로우·하네스를 자동으로 설계하는 방향(예: Automated Design of Agentic Systems, AFlow, Meta-Harness 등)으로 발전해 왔지만, 한 번 설계한 하네스가 다음 과제에 재사용될 수 있는 "경험"으로 축적되는 방법은 충분히 다루어지지 않았다. 저자들은 좋은 지도교수가 학생의 진행 상황을 보고 공유 실험 로그·재현 가능한 도구·검증 절차를 마련해주듯, Builder가 Target의 실행 결과를 관찰하며 "어떤 지원을 제공해야 하는가"에 대한 원칙을 학습할 수 있다는 아이디어에서 출발한다. 이때 Target이 과제를 어떻게 푸는지에 대한 지식(Task skill)과, Builder가 지원을 어떻게 설계해야 하는지에 대한 지식(Meta-skill)을 구분하는 것이 핵심 문제의식이다.

핵심 기여

  • 메타스킬(meta-skill) 개념 정의: 하나의 메타스킬은 (when, provide, use) 세 요소로 구성된다. when은 지원이 필요한 관찰 가능한 조건, provide는 제공해야 할 역량/자원, use는 Target이 그 지원을 어떻게 활용해야 하며 어떤 판단은 여전히 Target의 책임으로 남는지를 명시한다.
  • 구축-실행-반성(construction–execution–reflection) 루프: 빈 스킬 뱅크에서 시작해 개발 세트 과제들에 대해 Builder가 하네스를 만들고, Target이 실행한 결과(공개 실행 기록과 점수)를 Builder가 검토하여 스킬을 추가·수정·유지하는 절차를 제안했다.
  • 테스트 시점 적용: 학습이 끝나면 스킬 뱅크를 동결하고, 전체 뱅크를 모두 제공하거나 BM25 검색으로 최대 2개만 제공하는 두 방식으로 Builder가 과제별로 새로운 하네스를 구성하게 했다.
  • Builder에게 지식을 주는 것과 Target에게 직접 주는 것의 비교를 통해, 지식을 "운영화(operationalize)"하는 것 자체의 가치를 실증적으로 보였다.
  • 같은 모델이 Builder와 Target을 동시에 수행하는 동일 모델 자기개선(self-improvement) 가능성을 제시했다.

방법론

하네스 정책 H는 공개 과제 입력 x를 받아 기본 환경 H0을 확장한 실행 환경 Hx = H(x)로 매핑하며, 목표는 고정된 Target 실행 예산 Cx 안에서 기대 성능을 최대화하는 것이다. 개발 단계에서는 빈 뱅크 S0에서 시작해, 각 개발 과제에 대해 Builder가 현재 뱅크 전체와 공개 인터페이스를 이용해 하네스를 만들고, Target이 이를 실행하여 공개 실행 기록과 점수를 산출한다. Builder는 이 기록과 평가 피드백 F(e)를 검토하여, 배치마다 근거를 명시하며 최대 한 번의 '유지/수정/추가' 결정을 내려 뱅크를 갱신한다(S_{j+1} = Revise_B(...)). 두 번의 개발 세트 패스 후 뱅크는 동결되어 S가 된다. 테스트 시점에는 각 과제마다 전체 뱅크 혹은 BM25로 검색된 최대 2개의 스킬이 Builder에게 주어지고, Builder는 매번 새로운 환경에서 과제 전용 하네스 Hx를 구성하며 Target이 이를 실행해 최종 출력을 낸다. 하네스는 지시문, 메모리, 맥락 구성, 합성 도구, 실행 제어, 검증·복구, 작업공간 준비의 7개 선택적 구성 요소로 이루어지며, Builder는 각 요소를 과제에 맞게 직접 설계·구현한다. 실험에서는 GPT-5.6-Sol을 Builder로, Gemini-3.6-Flash·Qwen3.8-Flash·GPT-OSS-120B를 Target으로 사용했고, 모든 모델은 temperature 0, 높은 추론 노력(reasoning effort) 설정으로 구동되었다.

실험 설정 및 결과

평가는 에이전트 워크플로우 벤치마크인 Harness-Bench(106과제, 개발 11/테스트 95)와 상호작용형 과학 법칙 발견 벤치마크인 NewtonBench(324과제, 개발 32/테스트 292)에서 이루어졌다. 비교 대상은 (1) 지원 없는 기본 환경, (2) 빈 스킬 뱅크의 Builder, (3) 같은 메타스킬을 Target에게 직접 전달, (4) Target 자신의 경험으로 독립 학습한 구조화 스킬, (5) Target 궤적을 한 번에 정리한 자유형식 노트였다. 주요 결과는 다음과 같다. - 전체 뱅크를 받은 Builder의 거시 평균 성능은 65.31%로, 스킬이 없는 Builder보다 8.95%p, 같은 뱅크를 Target에게 직접 전달하는 경우보다 평균 12.02%p 높았고, 모든 6개 모델-벤치마크 조합에서 직접 전달 방식을 능가했다. - 전체 뱅크 제공이 BM25 상위 2개 검색 제공보다 6개 중 5개 설정에서 더 우수했다(NewtonBench에서 평균 +7.19%p). - 동일 모델이 Builder와 Target을 겸하는 세 가지 설정에서는 스킬 없는 구성 대비 평균 18.71%p 향상되어, 가중치 변경 없이도 "환경을 더 잘 설계하는 법을 배우는" 자기개선 경로가 가능함을 시사했다. - 하네스 구성 요소 중 '실행 제어기(controller)'를 제거하면 세 Target 모두 성능이 하락했으며(Gemini -13.36%p), 메모리+맥락 요소의 효과는 모델별로 엇갈렸다. - 결과(outcome) 전이 분석에서, NewtonBench의 '유효 제출 없음' 사례가 394→254건으로 줄고 정답 발견이 439→535건으로 늘어, 메타스킬이 과학적 탐구 루프의 완결성을 높였음을 보였다. - Builder나 Target을 교체하는 전이(transfer) 실험에서는 학습된 원칙이 다른 모델 조합에서도 어느 정도 재사용 가능했으나, 효과는 신뢰구간이 0을 포함하는 경우가 있어 불확실했고, 수신 측이 직접 학습한 뱅크가 가장 안정적으로 우수했다.

한계점

저자들이 스스로 명시한 한계로는, 본 연구가 하나의 주요 Builder 모델(GPT-5.6-Sol), 두 개의 벤치마크, 과제당 한 번의 실행 결과에 기반하고 있어 더 다양한 Builder와 과제에 대한 일반화는 추가 검증이 필요하다는 점이 있다. 또한 스킬 정제(refinement)가 항상 단조롭게 개선되는 것은 아니며(예: Qwen 모델에서 Harness-Bench 2차 패스 후 성능이 오히려 4.06%p 하락), 과도하게 최근 사례에 특화된 수정이 이루어질 위험이 있다고 지적했다. 교차 Builder/Target 전이 실험의 일부 신뢰구간은 0을 포함해 효과가 불확실했으며, 일반화 주장은 동일 벤치마크 내 미학습 과제로 한정되고 서로 다른 데이터셋이나 전혀 새로운 과제군으로의 전이는 향후 과제로 남겨두었다. 아울러 학습·구성에 드는 연산 비용과 성능 향상 간의 트레이드오프는 평가하지 않았다. 윤리 성명에서는 생성된 도구와 제어기가 의도치 않거나 유해한 동작을 가능하게 할 수 있으므로, 벤치마크 밖의 실제 응용에서는 권한 제한, 생성 구성요소 검증, 사람의 감독이 필요하다고 명시했다.

시사점

이 연구는 에이전트 성능 개선의 축을 "모델 자체의 능력 향상"에서 "모델을 둘러싼 지원 환경(하네스) 설계 능력의 향상"으로 확장할 수 있음을 보여준다. 즉, 지식을 그대로 전달하는 것보다 그 지식을 실행 가능한 도구·상태·제어 로직으로 "운영화"하는 중간 설계자(Builder) 역할 자체가 학습 가능한 대상이 될 수 있다는 것이다. 특히 동일 모델이 Builder와 Target을 겸할 때도 자기개선이 관찰되었다는 점은, 가중치 업데이트나 더 강한 외부 교사 모델 없이도 "스스로를 더 잘 뒷받침하는 환경을 설계하는 법을 배우는" 시스템 수준 자기개선 경로를 시사한다. 저자들의 표현을 빌리면, "더 나은 에이전트는 더 나은 조언자에서 시작될 수 있다."
