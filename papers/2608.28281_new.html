LoopArena: Benchmarking Models as Runtime Controllers for Loop Engineering

루프아레나: 루프 엔지니어링을 위한 런타임 컨트롤러로서의 모델 벤치마킹

한 줄 요약

코딩 에이전트를 감독하는 "루프 엔지니어링" 능력, 즉 별도의 모델이 실행 중인 코딩 에이전트에게 다음에 무엇을 할지 지시하고 언제 멈출지 판단하는 능력을 정량 평가하는 벤치마크 LoopArena를 제안한다.

배경 및 문제의식

최근 개발자들은 코딩 에이전트에게 매 프롬프트를 직접 작성하는 대신, 진행 상황을 모니터링하고 작업을 배분하며 검증을 수행하는 "루프"를 설계해 에이전트를 관리한다(루프 엔지니어링). 그러나 루프가 오래된 진행 노트를 신뢰하거나, 필요한 검증을 건너뛰거나, 예산을 잘못된 방향에 소모하거나, 안전하지 않은 상태에서 작업을 조기 종료할 위험이 있다. 기존 코딩 에이전트 벤치마크(SWE-bench 등)는 최종 결과만으로 성공·실패를 판정하기 때문에, 그 원인이 코딩 에이전트 자체의 능력 부족인지 루프의 지시 방식 문제인지 구분할 수 없다는 한계가 있다.

핵심 기여

  1. 런타임 루프 제어 벤치마크: 별도의 고정된 코딩 에이전트(Worker)를 감독하며 장시간 작업을 지시하는 모델(Controller)의 능력을 직접 평가 대상으로 삼는다.
  2. 통제된 비교 프로토콜: Controller 비교 시 Worker, 도구, 실행 예산, 평가자, 제어 인터페이스를 모두 고정하여 비교 대상을 Controller 모델 하나로 좁힌다.
  3. 세 단계 평가 체계: 개별 결정 단위(Type I), 작업의 일부 구간(Type II), 전체 작업(Type III)에서 각각 다른 비용으로 제어 능력을 평가하며, 세 설정 간 결과 일관성을 정량적으로 검증한다.

방법론

LoopArena는 Controller-Worker-Reporter 삼자 구조의 하니스를 사용한다. Worker는 유일하게 코드를 수정·실행할 수 있는 에이전트로, 할당된 구간을 ReAct 루프로 수행한다. Worker가 한 라운드를 마치면 임시 Reporter 에이전트가 대화 이력을 읽기 전용으로 요약해 "증거 패킷(Evidence Packet)"을 만들고, Controller는 이 패킷만 보고 다음 지시("Loop Contract": 진행/검증/중단)를 내린다. Controller는 코딩 도구에 직접 접근할 수 없고 오직 Worker에게 보내는 지시로만 영향을 미친다. 평가는 세 유형으로 구성된다: Type I은 사전에 실행·검증된 4지선다 문제로 Worker 실행 없이 평가하고, Type II는 준비된 중간 상태에서 작업의 한 구간만 실행하며, Type III은 원래 상태에서 전체 작업을 수행한다. 벤치마크는 SlopCodeBench와 BeyondSWE의 총 27개 소스 작업에서 구축되었다.

실험 설정 및 결과

Worker로는 Qwen3.7-Plus를 고정하고, Controller로 Qwen3.7-Plus, DeepSeek-V4-Flash, GLM 5.2, GPT-5.5, Claude Opus 4.8을 비교했다. Type III(전체 작업)에서 최고 성능인 GPT-5.5도 엄격 성공률(Strict Success Rate) 24.69%에 그쳐 장기 루프 제어가 여전히 어려운 과제임을 보였다. 목표를 매번 그대로 반복 지시하는 고정형(fixed control) 정책은 Type II에서는 성능을 끌어올렸지만(39.51%→46.91%) Type III에서는 무통제(no control)와 동일한 18.52%에 그쳐, 전체 작업에는 진행 상황에 적응하는 지시가 필요함을 시사한다. Type II는 Type III 대비 평균 64.4%의 추론 비용 절감을 보이면서도 Controller 순위가 유사하게 유지되었다(스피어만 상관계수 ρ=0.9747). Type I에서는 Contract 정확도가 72.22%~87.78% 범위였고, 어떤 단순 휴리스틱도 실제 Controller 성능에 근접하지 못했다.

한계점

현재 벤치마크는 저장소 단위 코딩 작업과 단일 Controller-Worker 구조에 한정되어 있다. 다양한 소프트웨어 도메인, 다른 Worker 계열 모델, 다중 Worker 환경, 다른 루프 조직 방식으로 확장하려면 추가 연구가 필요하며, 코딩 외 도메인으로 확장하려면 도메인별 작업 구성과 실행 가능한 평가자가 별도로 필요하다.

시사점

이 연구는 "에이전트를 지시하는 에이전트"라는 오케스트레이션 능력을 코딩 에이전트 성능과 분리해 직접 측정할 수 있는 틀을 제시한다. 저비용 Type II 평가가 고비용 Type III 평가와 높은 순위 상관을 보인다는 결과는, 향후 루프 제어 모델 개발 시 비용 효율적인 평가 파이프라인을 구성할 수 있는 실마리를 제공한다.
