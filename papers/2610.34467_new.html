DynaFlow: Learning Free-Form Multi-Agent Orchestration

다이나플로우: 자유 형식 멀티 에이전트 오케스트레이션 학습

DynaFlow는 메인 에이전트의 행동 공간에 자유형식 실행 가능 워크플로우 합성을 통합하여, 언제 협업이 필요한지 스스로 판단하고 작업에 맞는 멀티에이전트 워크플로우를 즉석에서 만들어내도록 학습하는 프레임워크이다.

한 줄 요약

DynaFlow는 메인 에이전트의 행동 공간에 자유형식 실행 가능 워크플로우 합성을 통합하여, 언제 협업이 필요한지 스스로 판단하고 작업에 맞는 멀티에이전트 워크플로우를 즉석에서 만들어내도록 학습하는 프레임워크이다.

배경 및 문제의식

대규모 언어모델(LLM) 기반 멀티에이전트 시스템(MAS)은 대개 사전에 설계된 역할, 통신 패턴, 워크플로우 구조를 고정된 형태로 사용한다. 그러나 실제 작업마다 요구되는 협업 형태는 다르다. 단순한 질의는 단일 에이전트로 충분하고, 독립적인 하위 작업은 병렬 처리가 유리하며, 서로 의존적인 단계는 상위 단계 결과를 신뢰성 있게 전달받아야 한다. 모든 상황에 동일한 고정 구조를 적용하면 불필요한 통신, 지연, 연산 낭비가 발생한다. DyFlow나 MAS-Orchestra 등 기존 자동 워크플로우 설계 연구도 제한된 연산자 템플릿을 사용하거나 중간 실행 결과를 보지 않은 채 한 번의 결정으로 전체 협업 구조를 생성하는 등 여전히 유연성에 한계가 있다. 저자들은 협업이 필요한 시점을 스스로 판단하고 문제 해결 과정에서 작업별 워크플로우를 구성하는 능력을 "자유 오케스트레이션(Free Orchestration)"이라 정의하고, 이것이 확장 가능한 MAS에 필요한 핵심 역량이라고 주장한다.

핵심 기여

  1. 자유형식 실행 가능 워크플로우 합성을 메인 에이전트의 행동 공간 자체에 통합한 DynaFlow 프레임워크를 제안했다. 메인 에이전트는 매 턴마다 직접 답변, 일반 도구 호출, 작업별 JavaScript 워크플로우 프로그램 생성 중 하나를 선택한다.
  2. 오케스트레이션 학습과 실행(서브에이전트) 능력 향상을 분리했다. 즉 서브에이전트들은 모두 고정한 채 메인 에이전트만 학습시켜, 기존에 학습된 모델을 그대로 실행자로 재사용할 수 있게 했다.
  3. 2단계 학습 절차를 설계했다. 1단계는 teacher 모델이 생성한 distillation trajectory로 지도 미세조정(SFT)하고, 2단계는 근거 없는 전제 주입, 편향된 검증, 정보 흐름 결함이 있는 예시를 걸러낸 고품질 부분집합으로 추가 정제한다.
  4. 수학·과학·멀티홉 질의응답을 포괄하는 6개 벤치마크(688문항)에서 Forced 모드 88.08%의 전체 정확도를 달성해 동일 백본을 사용한 최강 베이스라인 대비 10.90%p 높은 성능을 보였다.
  5. 워크플로우 구조 분석을 통해 학습이 상위 단계 결과의 명시적 활용, 검증, 정제를 늘린다는 것을 보이고, 단계 간 정보 흐름(cross-stage information flow)이 효과적인 멀티에이전트 오케스트레이션의 핵심 차원임을 제시했다.

방법론

DynaFlow는 메인 에이전트의 행동 집합을 일반 도구 호출(A_tool), 최종 답 출력(A_ans), 그리고 워크플로우 프로그램과 그 실행을 묶은 단일 행동 (P, W(P))으로 정식화한다. 메인 에이전트 정책은 질문, 작업 지시, 이전까지의 행동-관측 히스토리를 바탕으로 매 턴 하나의 행동을 생성한다(Algorithm 1). 워크플로우 프로그램 P는 agent 호출, parallel 실행, phase 라벨을 통해 서브에이전트의 역할·단계·의존 관계를 코드로 직접 정의하며, 독립적인 호출은 동시에 실행되고 의존적인 호출은 상위 결과를 명시적으로 전달받는다. 실행 결과 W(P)는 프로그램 출력과 각 서브에이전트 호출의 상태·출력을 담은 실행 트레이스를 함께 반환하며, 이는 히스토리에 누적되어 다음 행동 결정(추가 검증, 정제, 후속 워크플로우 호출 등)에 활용된다.

학습은 두 단계로 진행된다. 1단계(trajectory distillation)에서는 teacher 모델(GLM-5.3 Max)이 동일한 워크플로우 인터페이스로 생성한 trajectory 중 정답이 맞고 위임 프로토콜을 지킨 것만 남겨 2,031개 예시로 QLoRA 기반 SFT를 수행한다. 2단계(high-quality data selection)에서는 LLM judge가 프로그램과 실행 결과의 근거를 바탕으로 (i) 근거 없는 전제 주입(premise injection), (ii) 편향된 검증(verification defect), (iii) 정보 전달 누락·오류(information-flow defect) 세 가지 결함 여부를 평가하고, 결함이 없는 712개 예시만 선별해 더 작은 학습률로 추가 학습한다. 두 단계 모두 추론(reasoning) 토큰과 행동(워크플로우/답변) 토큰에 대해서만 손실을 계산하며, 질문이나 도구 정의 등은 마스킹한다. 평가는 Direct(도구/워크플로우 없이 바로 답변), Dynamic(직접 답변과 워크플로우 중 선택), Forced(반드시 워크플로우로 시작) 세 가지 실행 모드로 수행하며, 백본은 Qwen3.5-27B, 서브에이전트는 학습되지 않은 Base 체크포인트로 고정한다.

실험 설정 및 결과

AIME 2024/2025/2026(경시 수학), PolyMATH(다국어 수학, 200문항), GPQA-Diamond(대학원 수준 과학, 198문항), HotpotQA(웹 검색 기반 멀티홉 질의응답, 200문항) 등 총 688문항, 6개 벤치마크에서 평가했다. 비교 대상은 CoT, CoT-SC, Self-Refine, AFlow(모두 Qwen3.5-27B 기반)와 학습 전 Base 메인 에이전트의 Direct/Dynamic/Forced 결과다.

DynaFlow는 Forced 모드에서 전체 88.08%, Dynamic 모드에서 87.94%를 기록했으며, 최강 베이스라인인 AFlow(76.45%)보다 10.90%p 높았다. 세부적으로 AIME 2024/2025/2026 전체를 Forced 모드에서 100% 정답 처리했고, PolyMATH는 기존 최고 대비 3~4%p, GPQA-Diamond는 Base Forced 대비 7.07%p, HotpotQA는 웹 검색을 활용한 Base 대비 6~7%p 향상했다. 흥미로운 점은 학습 전에는 워크플로우(Base, Forced)가 오히려 직접 답변(Base, Direct)보다 HotpotQA를 제외한 모든 벤치마크에서 성능이 낮았으나, 학습 후에는 Forced 모드가 모든 벤치마크에서 Direct와 동등하거나 상회했다는 것이다. 이는 오케스트레이션 학습이 있어야만 협업이 실제로 도움이 됨을 보여준다.

워크플로우 구조 분석에서는 학습이 진행될수록 병렬·순차를 혼합한 하이브리드 구조의 비중이 3.4%(Base)에서 85.6%(2단계 후)로 크게 늘었고, 상위 단계 출력을 명시적으로 활용하는 프로그램의 비중도 12.6%에서 97.7%로 증가했으며, 주요 정보 흐름 결함은 1.9%에서 0.9%로 감소했다. Dynamic 모드는 전체 질문의 47.1%를 워크플로우 없이 직접 답하면서도 Forced 대비 정확도 격차가 0.14%p에 불과했고, 질문당 평균 서브에이전트 수도 2.44개로 Forced(약 4.16개)보다 적었다. 벤치마크별 역할 배분을 보면 AIME·PolyMATH는 Solver와 Verifier가 90% 이상을 차지하고, HotpotQA는 Researcher가 59.6%, GPQA-Diamond는 Solver(41.6%)와 Researcher가 함께 상당한 비중을 차지하는 등 작업 특성에 맞춘 역할 구성이 나타났다.

한계점

논문에 별도의 "한계점(Limitations)" 절은 없으나, 논의(Discussion) 절에서 다음과 같은 한계와 향후 과제를 언급한다. 첫째, 서브에이전트는 학습되지 않고 고정되어 있어 정보 전달의 신뢰성이나 독립적 검증 능력 자체는 향상되지 않는다. 둘째, GPQA-Diamond 실패 사례 분석에서 서브에이전트가 만든 잘못된 중간 결론이 이후 검증 단계를 오도하거나, 메인 에이전트가 최종 답을 종합할 때 올바른 증거를 우선시하지 못해 정보가 소실·덮어쓰기되는 경우가 확인되었다. 셋째, 현재 학습은 첫 턴(first-turn) 추론과 워크플로우 합성에 대한 지도학습에 국한되며, 상충하거나 오류가 있는 다중 턴 trajectory에 대한 지도는 다루지 않는다. 저자들은 향후 서브에이전트의 정보 전달·독립 검증 능력을 함께 학습시키고, 충돌하는 출력 평가, 오류 식별, 오류 복구, 워크플로우 수정, 최종 답 선택을 포함하는 멀티턴 지도로 확장하는 것을 과제로 남겼다.

시사점

DynaFlow는 "언제, 어떻게 협업할지"를 결정하는 오케스트레이션 능력을 메인 에이전트의 명시적이고 학습 가능한 기능으로 분리함으로써, 실행 주체(서브에이전트)의 능력을 전혀 향상시키지 않고도 오케스트레이션 학습만으로 큰 성능 향상을 얻을 수 있음을 보여준다. 특히 학습 이전에는 협업(워크플로우)이 오히려 성능을 떨어뜨렸다는 결과는, 협업 자체가 항상 이득이 되는 것이 아니라 언제 협업할지와 협업을 어떻게 조직할지를 동시에 학습해야 진정한 효과를 볼 수 있음을 시사한다. 또한 상위 단계 결과를 하위 단계로 명시적으로 전달·검증·정제하는 단계 간 정보 흐름이 효과적인 멀티에이전트 오케스트레이션 설계의 핵심 축이라는 통찰을 제공하며, 향후 자동화된 워크플로우 생성 및 멀티에이전트 시스템 설계 연구에 중요한 참고점이 될 수 있다.
